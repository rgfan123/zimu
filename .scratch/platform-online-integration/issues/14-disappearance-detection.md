# 14 — 消失检测语义与规范修订

> 本票是合并新增：用户裁定**不按各平台状态枚举分别实现 `pullOrderChanges` / `pullCancellations`**，改为跨平台统一的「消失检测」。理由是飞象无 JSON 接口根本无解、聚福宝取消态枚举至今未抓到，而「上次在待发货列表、这次不在」的差分对三平台通用。

**What to build:** 拉取后的跨平台差分机制：已确认但从平台待发货列表消失的订单 → 生成复核事项。**差分只出信号，绝不静默改已确认的单**（不可变铁律）。需新增 `SOURCE_STATUS_CHANGE` 原因码（`excel-closed-loop-spec.md` §11 白名单修订，属规范级改动需评审）。

**为什么要做：** 客户在平台取消了单，而我们已经生成履约导出发给京东——货就白发了。这是这个机制存在的唯一理由。

**要裁的语义（开工前先定）：**
- 比对基线：上次拉取快照（平台视角）/ 系统内已确认未发货集合（系统视角）/ 两者交集。**建议交集**，可同时挡掉「还没拉到」与「平台分页漂移」两类误报
- 防抖：单次不在就报，还是连续 N 次？**建议连续 2 次**
- 误报排除：**我们自己刚回填完发货**是最大误报源（回填是人工触发，与拉取无固定先后）→ 建议按「该单已有推送成功记录」直接排除
- 复核事项落订单级还是行级（`ProcessingStage` 行级权威、`OrderProgressSummary` 订单级摘要）
- 原因码粒度：一个 `SOURCE_STATUS_CHANGE` 够，还是要分「疑似取消」「疑似被他方发货」。**建议只加一个**，具体写正文——我们其实分辨不了，除非 16 拿到聚福宝状态枚举全集
- 已发出履约导出后才检测到消失：复核事项要给操作员什么信息、能做什么动作（`FulfillmentExport` 定义是「文件一旦生成即形成履约承诺，不能覆盖原指令」，大概率只能人工联系履约方拦截）
