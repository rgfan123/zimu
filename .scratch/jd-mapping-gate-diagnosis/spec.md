# 京东 SKU 映射门禁：诊断分类与如实呈现

状态：Ready for tickets
日期：2026-08-28
诊断基线：`jry/integration-20260828`（生产在跑的代码），生产库只读核实
范围：**只管「映射门禁的诊断与呈现」**。相邻问题（死代码双重包装、订单关闭态、批次作用域）各自另立规格，本文只在「依赖关系」一节注明耦合点。

---

## Problem Statement

用户原话：**「SKU映射我们不是有吗？为什么会显示没有？」**

他没记错。生产至今门禁一共只阻断过 6 次、涉及 2 个发货批次，**其中 0 次是「没配映射」**：

| 发货批次 | 次数 | 真实原因 | 系统显示 |
|---|---|---|---|
| shipment 1 | 4 | `JD_GOODS_QUERY_FAILED`：京东返回 471「时间戳已失效」——我方请求签名时钟问题 | 「京东 SKU 映射门禁未通过，请先维护映射并重新核对」 |
| shipment 17 | 2 | `UNIT_CONVERSION_MISSING`：订单行 `unit_snapshot` 是占位符「来源数量单位」，而 SKU 真实单位就是「件」 | 同上一句话 |

shipment 1 的映射链路每一环都健康（`SKU-JD-000032` → `provider_skus.provider_sku_code = EMG4418904462756`，active，`jd_pieces_per_unit=1`），门禁自己算出的逐项明细里也白纸黑字写着 `JD_GOODS_QUERY_FAILED（471）`。京东恢复后门禁自愈转 PASSED，期间 SKU 与映射数据一个字都没改。

shipment 17 更糟：运营**照着系统的话做了无用功**——给一个单位本来就是「件」的 SKU 手工补了一条冗余的换算系数，补完 0.4 秒后门禁就过了。系统骗着人去改了一个根本不需要改的东西，还留下了一条永久的脏配置。

用户看到的三个具体故障：

1. **文案说谎。** 门禁有 14 种阻断原因，性质迥异（本地漏配 / 外部瞬时故障 / 外部数据漂移），但在库存核对那一跳全部塌缩成同一个外层码 `JD_SKU_MAPPING_GATE_BLOCKED` 和同一句「请先维护映射」。真实原因被降级塞进一个附属字段 `mapping_issue_code`，而这个字段**在前端没有任何读取方**。
2. **身份丢失。** 发货台摘要行取 `productName ?? goodsNo ?? code`，通用 blocker 前两者皆空，屏幕上直接打印裸码 `JD_SKU_MAPPING_GATE_BLOCKED`；复核抽屉的「阻断码」列同样直接渲染裸码；就地处置面板显示「（无商品名）」+「该阻断未定位到具体订单行，暂不能直接换货」。前端其实有一张覆盖全部 14 码的中文标签表 `ISSUE_LABELS`，但它只喂给 `detail.affected_shipment_items`，**从没接到 blockers 的渲染路径上**。
3. **真相被派到了别人的队列。** 同一次门禁运行会并行写两条复核事项：`JD_SKU_MAPPING`（责任团队 `SKU_OPS`，**带真实原因**）与 `JD_STOCK`（责任团队 `FULFILLMENT_OPS`，**只带误导文案**）。发货台按当前岗位过滤责任团队，一个发货岗运营在自己队列里只能看到写着「请先维护映射」的那条，看不到写着「京东查询失败 471」的那条。

再加上两条只有翻代码才会知道、但直接决定运营体验的事实：

4. **不管哪种原因，自救动作永远是同一个**：`OPEN_SKU_MAPPING` → `/product/sku-mappings`，责任团队永远 `SKU_OPS`，复核事项标题永远「京东商品映射未通过」。京东时间戳失效也会被这样派单。
5. **外部瞬时故障不产生任何运营告警**，运维侧完全看不见。生产 `operational_alerts` 里没有任何 JD_SKU_MAPPING 类告警——同一个仓库里，库存判定层（`FulfillmentStockDecisionService`）遇到京东查询失败是会开 `JD_STOCK_QUERY_FAILED` 告警的，门禁层没有。

### 对任务简报的两处更正（重要，影响票的划分）

- **简报说「生产那条空明细记录走了防御性兜底」——不成立。** 逐项透传与兜底是同一个 commit（`ef37bea1`，2026-08-27 18:36:05）引入的；生产那两条空明细复核事项创建于 08-25 12:37 与 08-27 17:42，**都早于该 commit**，是旧版本的产物。该 commit 之后生产再没产生过 BLOCKED 门禁运行，所以逐项透传这条修复**在生产是零验证的**。兜底分支在当前 HEAD 里是不可达死代码（BLOCKED ⟺ 存在非空 issues ⟺ blockingItems 非空，同一层循环同一份列表派生），且无任何测试覆盖。
  → 结论：**别再花力气修一个已经修过的东西**，要做的是给它上不变式测试并把真相接到界面上。
- **简报的 12 码表不完整。** 实际是 **14 种阻断码 + 2 种仅告警码**。漏掉的三种是 `UNIT_CONVERSION_MISSING` / `UNIT_CONVERSION_INVALID` / `NON_INTEGRAL_QUANTITY`——而生产两次真实阻断中的一次恰恰命中的就是第一个。`NAME_MISMATCH` 其实是**告警不是阻断**（另一个告警码是 `GOODS_STATUS_UNKNOWN`）。

## Solution

一句话：**门禁按「谁该动手、下一步做什么」给失败分类，界面照实说，明细完整性由机制保证而不是靠人记得填。**

四件事：

1. **分类。** 14 种阻断原因归入 4 个处置族，族决定文案、决定责任团队、决定维护动作。
2. **外部瞬时故障不再冒充配置缺失。** 单独的阻断码 + 单独的责任团队 + 运营告警 + 诚实文案；仍然阻断（fail-closed，查不到不等于可以发货），但阻断的语义从「你配错了」变成「暂时核不了，已通知运维」。
3. **明细完整性机制化。** 「BLOCKED 必须带逐项明细」升级为契约不变式并有测试钉死；「14 个 issue code 必须有中文标签」纳入既有的构建期对账测试；再也不靠「记得填」。
4. **发货前可见的京东映射就绪度视图。** 让缺口在建档时被看见，而不是发货时被拦。

### 失败分类表（这是本规格的核心决策）

| 处置族 | issue code | 谁该动手 | 下一步 |
|---|---|---|---|
| **A. 本地配置缺失/失效**<br>`LOCAL_CONFIG` | `INTERNAL_SKU_MISSING`<br>`INTERNAL_SKU_INACTIVE`<br>`MAPPING_MISSING`<br>`MAPPING_INACTIVE`<br>`GOODS_NO_MISSING`<br>`UNIT_CONVERSION_MISSING`<br>`UNIT_CONVERSION_INVALID` | SKU_OPS | 去 SKU 映射维护页补/启用配置，补完重跑门禁 |
| **B. 本地数据口径**<br>`LOCAL_DATA` | `NON_INTEGRAL_QUANTITY` | FULFILLMENT_OPS | 数量与换算系数得不到精确整数件；要么改换算系数（SKU_OPS），要么改发货数量口径。**不是「没配映射」** |
| **C. 外部瞬时故障**<br>`EXTERNAL_TRANSIENT` | `JD_GOODS_QUERY_FAILED` | FULFILLMENT_OPS + 运维 | 京东只读查询没打通，与映射无关。已开运营告警；稍后重跑；持续失败找运维查签名/时钟/凭据 |
| **D. 外部事实 / 数据漂移**<br>`EXTERNAL_FACT` | `JD_GOODS_NOT_FOUND`<br>`GOODS_NO_CONFLICT`<br>`ERP_GOODS_NO_CONFLICT`<br>`GOODS_STATUS_MISSING`<br>`GOODS_DISABLED` | SKU_OPS + 京东侧 | 京东那边的商品状态/编码与我方映射对不上，去京东后台核对；不是我方漏配 |
| **（告警，不阻断）** | `GOODS_STATUS_UNKNOWN`<br>`NAME_MISMATCH` | 知晓即可 | 当前完全不可见，见下 |

顺带修一个文案 bug：`INTERNAL_SKU_INACTIVE` 的判定是 `sku != null && sku.active()` 取反，**`skus` 行整行不存在时也报「内部 SKU 已停用」**。缺行与停用是两回事，文案必须分开。

### 瞬时故障该不该阻断？重试语义是什么？

**该阻断，fail-closed 不变。** 京东商品事实核不上就发真实出库单，风险不可接受——门禁自己在另一处已经确立了这条原则的边界：未文档化的 `enableFlag` 取值走告警而非阻断，理由写在注释里「真正的硬关卡是 `queryStock` 库存校验」。查询**失败**和取值**未文档化**不是一回事，前者连事实都没拿到。

改的不是「阻不阻」，是**阻断的语义、派单对象和可见性**。

重试语义（明确写死，避免实现时发挥）：

- **只对传输/网关类失败重试**：`CLIENT_EXCEPTION`、`NO_RESPONSE`。有限次数、指数退避，**在同一次门禁运行内完成**。
- **不对业务语义失败重试**：`JD_GOODS_NOT_FOUND`、`GOODS_DISABLED`、编码冲突类——重试它们只是浪费配额。
- **京东返回的业务码（如 471）默认不重试**，除非建立了明确的可重试码白名单。如实说明：**471「时间戳已失效」是持续状态（签名时钟漂移），当场重试大概率同样失败**——所以重试不是这一类的治疗手段，分类 + 告警 + 诚实文案才是。把重试当成 471 的解药会得到一个跑得更慢、错得一样的门禁。
- **绝不引入跨运行缓存把 BLOCKED 结论固化。** 门禁每次用全新幂等键重跑外部查询，这**不是缺陷是设计**：生产已实测 shipment 1 在 BLOCKED→PASSED 全程 `local_gate_fingerprint` 一字未变，本地事实完全相同、结论却随京东恢复而改变。若把内层幂等键稳定化成「shipment + 本地指纹」，第一次 471 的 BLOCKED 快照会被无限重放，京东恢复永远观测不到——那正是用户报的这个症状的完美制造机。任何后续的缓存/批量优化方案（另立规格）必须先满足「瞬时失败结论不得被缓存」这条前置约束。

### 明细丢失如何在机制上杜绝

四个机制，都不依赖人的记性：

1. **不变式测试**：任一 `gate_status=BLOCKED` 的响应，`affected_shipment_items` 必须非空，且每个 item 的每条 issue 必须带 `code`。这在代码结构上已恒真（`blockingIssues` 与 `blockingItems` 由同一层循环同一份 `issues` 列表派生），但**没有任何测试钉死它**，谁都可以在下一次重构里悄悄拆散。
2. **兜底不再伪造事实**：当前「拿不到明细就补一条通用文案 blocker」的兜底路径，制造出的正是生产里那两条说谎的记录。改为：拿不到明细时**显式失败并留痕**（抛出 + 审计），而不是编一条说得通但是错的 blocker。伪造一条说谎的阻断项比失败更糟——失败会被发现，说谎不会。
3. **空 observations 说清楚为什么**：门禁挡下时京东库存查询根本没发起，`observations: []` 是设计不是丢数据。响应要显式带上「因映射门禁未通过，本次未查询京东库存」的结构化标记，界面照此渲染，而不是给用户一张无解释的空表让他以为数据丢了。
4. **构建期标签对账**：14 个 issue code 纳入既有的枚举↔标签对账测试（后端新增枚举值缺前端中文标签即 CI 失败）。未登记码按 UIUX-03 既定兜底回退显示技术原码——诚实呈现，**禁止「未分类原因」类掩盖性文案**。

### 事件流要能回答「为什么」

当前 `JD_SKU_MAPPING_CHECKED` 事件的 payload 只有计数（gate_status / checked_mapping_count / blocking_issue_count / warning_count），不含任何 issue code；`JD_STOCK_CHECKED` 的 `blocker_codes` 是塌缩后的码。结果是**没有任何 SQL 能统计「多少次是京东抖动、多少次是真的没配映射」**——而这恰恰是本该早就报警的那个指标。低成本高价值：把 issue code（及处置族）写进事件 payload。

顺带解决 `review_cases.detail` 就地覆盖的历史销毁：shipment 1 跑了 4 次 BLOCKED，复核事项 detail 里只剩最后一次，前三次的原因在该表里已不可复原。事件流承担历史后，detail 覆盖就只是「当前态」而不是唯一记录。

### 映射就绪度视图（发货前可见）

生产 92 个启用 SKU 中 31 个没有启用的京东映射。**但「34% 无映射」这个数字口径不对，实现时必须先厘清**：

- 31 个里有 5 个是 `SKU-TP-*` 前缀（第三方履约线）。按领域词汇表，SKU 编号格式是 `SKU-{provider_code}-{序号}` 且「每个 SKU 一期固定归属一个履约方」——第三方线的 SKU **本就不需要京东映射**，把它们算进缺口是虚报。
- 真实的京东线缺口是 **26 个 `SKU-JD-*`**，且**不是历史积累**：其中 24 个的 `created_at` 完全相同（2026-08-28 11:46:53），另 2 个同日 14:19——是当天两次批量建档只建了 SKU、没同步建 `provider_skus` 造成的**当天新缺口**。
- 分母该用「京东线启用 SKU」而不是「全部启用 SKU」。确切分母需要按履约方归属重算，本次诊断未核实到已映射的 61 条里各前缀的分布，**不要照搬 34%**。

视图口径（这是本节唯一的硬要求）：**从 `skus` 出发 LEFT JOIN 映射**，而不是反过来。既有的「京东件数换算候选」列表是最接近的先例，但它遍历的是已有映射，**压根没映射的 SKU 永远不会出现在里面**——那正是它的盲区，新视图不能重蹈。

每行应能回答四问：内部 SKU 是否启用 / 是否有启用的京东映射 / `goodsNo` 是否非空 / 非「件」单位是否配了换算系数。这四问与分类表的 A 族一一对应，即：**这个视图列出的就是「将来会以 A 族原因被门禁挡下」的 SKU**。

边界：**就绪度视图是事前提示，不是门禁**。不得用它替代门禁判定，也不得据它在发货台新增拦截。

### 顺带发现的两个未触发的 fail-open 漏洞（本规格一并覆盖，因为同属门禁判定路径）

门禁的入口校验只断言「不是京东云仓则拒绝」和「发货批次的 item 非空」，**没有对被检查的 SKU 数量作任何下限断言**，而 `passed` 只看 `blockingIssues == 0`。于是两条路径会以 `checked_mapping_count=0` **判定通过并放行**：

1. `CUSTOM_BUNDLE` 订单行在组件表里没有任何组件行 → 0 次检查、0 条 issue → PASSED。生产现状：`CUSTOM_BUNDLE` 9 行、零组件 0 行，未触发。
2. 组件行引用的 SKU 在 `skus` 表里不存在 → 组件查询是 `JOIN app.skus`（内连接），该组件被**静默丢弃**，同样不产生 issue。

「一个都没检查」必须判 BLOCKED，不能判 PASSED。

## User Stories

1. 作为发货运营，我希望阻断卡片上写的是这次真正发生了什么（「京东商品查询失败」），而不是一句放之四海皆准的「请先维护映射」，这样我不会去改一个根本没坏的东西。
2. 作为发货运营，我希望阻断卡片显示是**哪一个商品**被挡了（商品名 + 京东商品编号 + 内部 SKU 编码），这样我不用拿着一个裸码去主数据页反查。
3. 作为发货运营，我希望在自己的队列里就能看到真实原因，而不是真相被写在另一个岗位的队列里。
4. 作为发货运营，当京东接口临时不可用时，我希望看到「稍后重试」而不是「去配映射」，这样我不会为一次网络抖动做半小时无用功。
5. 作为发货运营，当阻断是京东那边商品被停用时，我希望被告知去京东后台核对，而不是被指向我方的映射维护页。
6. 作为发货运营，我希望「下一步该做什么」是随原因变化的，而不是永远同一个按钮跳同一个页面。
7. 作为发货运营，我希望复核事项抽屉里的「阻断码」列显示中文，未登记的码才回退显示原码。
8. 作为发货运营，当门禁挡下、库存根本没查时，我希望界面明说「本次未查询京东库存」，而不是给我一张空表让我以为数据丢了。
9. 作为发货运营，我希望阻断卡片上的案件号能整段复制、不被后面的计数数字污染。（与 frontend-audit-fixes 票 09 同源，见依赖关系）
10. 作为 SKU 运营，我希望「缺映射」和「映射已停用」是两条不同的提示，因为处置动作不同。
11. 作为 SKU 运营，我希望「内部 SKU 不存在」和「内部 SKU 已停用」是两条不同的提示，不要把找不到的行说成停用的行。
12. 作为 SKU 运营，我希望在**建档时**就知道哪些启用 SKU 还没有京东映射，而不是等它被发货流程拦下来。
13. 作为 SKU 运营，我希望就绪度视图能区分「没有映射」「映射停用」「goodsNo 为空」「缺换算系数」四种不同的缺口。
14. 作为 SKU 运营，我希望就绪度视图不把第三方履约线的 SKU 算成京东缺口，否则这张表天天飘红、没人再看。
15. 作为 SKU 运营，我不希望系统诱导我为一个单位本来就是「件」的 SKU 补一条冗余换算系数——那会在主数据里留下永久的脏配置。
16. 作为运维，我希望京东只读查询失败会产生运营告警，这样我能在运营发现之前就知道接口出问题了。
17. 作为运维，我希望告警里带得上京东返回的业务码与请求标识，这样我能直接定位是签名、时钟还是配额问题。
18. 作为运维/负责人，我希望能用一条 SQL 回答「这个月门禁阻断里，多少次是外部故障、多少次是我们真的漏配」，这是评估映射工作量的唯一依据。
19. 作为负责人，我希望同一个发货批次多次重跑的历史原因不被就地覆盖销毁，这样事后能复盘「它到底为什么卡了三次」。
20. 作为负责人，我希望「京东商品名称与我方不一致」这类告警是可见的，而不是只存在于幂等快照的深处、界面永远看不到。
21. 作为开发者，我希望「门禁判 BLOCKED 就必须带逐项明细」是一条有测试保护的契约，而不是一条只存在于注释里的君子协定。
22. 作为开发者，我希望后端新增一个 issue code 而前端忘了加中文标签时 CI 会红，而不是等它裸码上屏被用户看到。
23. 作为开发者，我希望拿不到逐项明细时系统显式失败并留痕，而不是编一条通用文案糊弄过去——生产那两条说谎的记录就是糊弄的产物。
24. 作为开发者，我希望阻断项携带的处置族是一等字段，这样责任团队与维护动作都由它派生，不必在三个地方各写一遍 if。
25. 作为开发者，我希望「一个 SKU 都没检查」被判成阻断而不是通过，这样零组件礼包和悬空组件引用不会静默放行到真实出库单。
26. 作为开发者，我希望重试范围被明确限定在传输类失败，不会有人把它扩大成「所有失败都重试三次」然后把京东配额烧掉。
27. 作为开发者，我希望这次改动不引入任何跨运行的门禁结论缓存，因为那会把瞬时失败固化成永久阻断。
28. 作为业务同事，我希望阻断卡片上显示的商品名是平台名称（我在平台单上能对上的那个），内部名降为次要信息。（与票 09 同源）
29. 作为使用系统的人，我希望系统在不知道的时候说不知道，而不是给我一个听上去很确定但是错的原因。

## Implementation Decisions

### 门禁侧（`ShipmentJdSkuMappingGateService` 及其只读核验器）

1. **每条 issue 增加处置族字段**（4 值枚举：`LOCAL_CONFIG` / `LOCAL_DATA` / `EXTERNAL_TRANSIENT` / `EXTERNAL_FACT`）。族是**决策字段不是展示字段**：责任团队、维护动作、是否开运营告警、文案模板都由它派生，不在多处重复判断。
2. **维护动作由族派生，不再无条件返回 `OPEN_SKU_MAPPING`。** A 族指向 SKU 映射维护；C 族指向「稍后重跑 + 已通知运维」；D 族指向「京东后台核对」并保留重跑入口；B 族指向数量/换算口径。
3. **复核事项责任团队由族派生**：A/D → `SKU_OPS`；B/C → `FULFILLMENT_OPS`。同一次运行若跨族，按最严重/最主要族归属并在 detail 里保留全部族分布（避免一次运行拆成多张单）。
4. **`INTERNAL_SKU_MISSING` 与 `INTERNAL_SKU_INACTIVE` 之外补一个「SKU 记录不存在」的语义**，或至少把「行不存在」与「已停用」的文案分开。当前二者共用一个判定。
5. **有限重试仅覆盖传输类失败**（客户端异常 / 无响应），有限次数 + 退避，同一次门禁运行内完成，不跨运行。京东业务码默认不重试。重试次数与退避是常量（可配置、有默认），不是散落的魔法数。
6. **外部瞬时故障开运营告警。** 直接沿用库存判定层「京东查询失败 → `JD_STOCK_QUERY_FAILED` 运营告警」的既有模式与严重级别口径，新增门禁侧的告警类型，携带业务码与请求标识。告警落库须与业务事务解耦（既有做法：独立事务提交，不被业务回滚吞掉）。
7. **入口校验补下限断言**：`checked_mapping_count == 0` 判 BLOCKED，附带明确原因（零组件礼包 / 组件引用的 SKU 不存在）。组件加载的内连接语义要么改为外连接并显式报错，要么在加载后比对组件行数与解析出的 subject 数不一致即报错。
8. **事件 payload 增加原因维度**：`JD_SKU_MAPPING_CHECKED` 除计数外带上本次命中的 issue code 集合与族分布，使「外部抖动 vs 真漏配」可用 SQL 聚合。
9. **不引入任何跨运行的门禁结论缓存**，内层幂等键保持每次全新。这是本规格的显式约束，写进代码注释。

### 塌缩点（`ShipmentJdStockCheckService` 的 blocker 出口）

10. **阻断项的 `code` 改为真实 issue code**（如 `JD_GOODS_QUERY_FAILED`），不再恒为 `JD_SKU_MAPPING_GATE_BLOCKED`。理由：既有的中文标签对账机制与「未登记码回退显示原码」的兜底契约都按 `code` 工作，一个永远塌缩的外层码保证了标签表永远帮不上忙。兼容性代价可接受——前端全量检索 `JD_SKU_MAPPING_GATE_BLOCKED` **零命中**，没有任何消费方在按它分组。
11. **保留家族归属**：阻断项另带「来自映射门禁」的家族标记与处置族，供需要粗粒度分组的消费方使用。现有的 `mapping_issue_code` 附属字段随之取消（它写了但全链路无人读，等于写进黑洞）。
12. **门禁阻断时的响应显式标注库存查询未发起**及其原因，而不是只留一个空的观测列表。
13. **阻断项继续携带商品身份**（商品名 / 京东商品编号 / SKU 编码 / 订单行）——这部分逻辑 `ef37bea1` 已实现但**生产零验证**，本次的任务是给它上测试并接到界面，不是重写。

### 前端（发货台 + 复核抽屉 + 就地处置面板）

14. **单一标签表接到阻断项渲染路径上。** 既有覆盖 14 码的中文标签表沿用，不另起第二张表；把它接到 blockers 的渲染上（当前它只服务 `affected_shipment_items`）。
15. **裸码不再作为商品名的兜底。** 商品名缺失时显示明确的「未定位到商品」而不是把阻断码打印在商品名的位置。
16. **复核抽屉的「阻断码」列显示中文**，未登记码回退原码（UIUX-03 兜底契约）。
17. **为映射门禁类复核事项补上事实组配置**，使抽屉能渲染原因、商品身份与下一步；当前无配置，回落到白名单渲染后只剩「发货批次编号」一行。
18. **下一步动作按钮随族变化**：A 族「去维护映射」，C 族「稍后重跑」，D 族「去京东后台核对 + 重跑」。
19. **告警类（`GOODS_STATUS_UNKNOWN` / `NAME_MISMATCH`）在通过时也要可见**，作为不阻断的提示呈现，而不是只存在于幂等快照深处。

### 主数据（就绪度视图）

20. **新增只读的京东映射就绪度查询**，从启用 SKU 出发 LEFT JOIN 京东映射，逐行给出四问的答案。
21. **只统计京东履约线的 SKU**，分母口径在实现时按履约方归属确定，不照搬「34%」。
22. **入口放在 SKU 映射维护页**（事前），发货台不新增拦截，不改门禁判定。

### 契约与文档

23. 阻断项 JSON 形状变化须同步 OpenAPI 与 API 契约文档（既有契约一致性门禁会强制）。
24. 新增的运营告警类型与复核原因码须同步中文标签表（既有构建期对账测试会强制）。

## Testing Decisions

### 什么是好测试

只测**外部可见行为**：给定京东侧返回什么，HTTP 响应里的阻断码、处置族、责任团队、文案、维护动作是什么；界面投影函数吃进这份 JSON 吐出什么。不断言私有方法、不断言内部 Map 的键顺序、不为了覆盖率去测兜底分支的实现细节。

### 测试缝（seam）——优先复用既有缝，不新增

| 后端主缝 | `POST /api/v1/shipments/{id}/jd-sku-mapping-check` 与 `.../jd-stock-check` 的公开 HTTP 端点；京东侧通过对基础资料服务打桩注入具体业务码（471 / 1000 / 空商品列表 / 抛异常） | `ShipmentJdSkuMappingGateApiTest`、`ShipmentJdStockCheckApiTest` |
| 外部失败降级 | 同上，断言运营告警与审计在业务事务之外落库 | `FulfillmentStockDecisionJdFailureTest` |
| 只读核验器 | 单元级，仅在需要区分「传输失败 vs 业务码失败 vs 空结果」时使用 | `JdGoodsReadOnlyVerifierTest` |
| 前端 | 纯投影模块 + `node:test`，无 React 无 fetch | `stockBlockerCases.test.ts`、`jdSkuMappingReview.test.ts`、`blockerGrouping.test.ts` |

**新增缝：0。** 需要确认的一点：把 14 个 issue code 纳入构建期对账测试，意味着要给该测试新增一条「从门禁服务源码提取 issue code」的提取规则（该测试已有 R1–R7 七条提取规则的先例，形态一致）。**这一点请与提出人确认是否接受**——它是本规格唯一对既有测试基础设施的结构性扩展。

### 必须有的用例

1. **京东返回 471** → 阻断码 `JD_GOODS_QUERY_FAILED`，族 `EXTERNAL_TRANSIENT`，文案不含「请先维护映射」，责任团队非 `SKU_OPS`，产生运营告警。（回归 shipment 1）
2. **真·缺映射** → 阻断码 `MAPPING_MISSING`，族 `LOCAL_CONFIG`，维护动作指向 SKU 映射维护页。
3. **占位符单位 + SKU 真实单位是「件」** → 不阻断。（回归 shipment 17 的假阳性；单位口径的 COALESCE 修复目前**没有测试**，这条要补上钉死）
4. **BLOCKED 必带逐项明细**（不变式）：任一阻断响应的受影响项非空，且每条 issue 带 code。
5. **门禁阻断时** → 响应显式标注未查询京东库存，且不写任何库存快照行。
6. **零组件礼包** → 判 BLOCKED（当前会 PASSED，测试先红）。
7. **组件引用的 SKU 不存在** → 判 BLOCKED（当前静默丢弃，测试先红）。
8. **传输类失败重试**：桩连续失败 N-1 次后成功 → 门禁 PASSED 且只产生一次阻断记录；桩持续失败 → 阻断且重试次数有上界（不无限打京东）。
9. **业务码不重试**：桩返回商品未找到 → 只调用一次。
10. **事件 payload 含 issue code**：一条 SQL 能按原因分组统计。
11. **告警码不阻断**：京东返回未文档化的启用标志 / 名称不一致 → gate PASSED，但告警在响应里可见。
12. **前端**：14 个 code 全部有中文标签；未知 code 回退裸码；商品身份缺失时不把阻断码打印在商品名位置。
13. **前端**：复核抽屉对映射门禁类事项渲染出原因与商品身份，而不是只有「发货批次编号」一行。
14. **就绪度视图**：一个有 SKU 但完全没有映射行的 SKU **必须出现在结果里**（这是既有「换算候选」列表的盲区，必须被钉死）；第三方线 SKU 不出现。

### 不做的测试

- 不为当前那条不可达的兜底分支写覆盖测试——它要被改成显式失败，测的是「显式失败」这个新行为。
- 不测京东真实接口。所有京东侧行为通过打桩注入；测试须显式钉住 MOCK 客户端模式，避免操作者环境的 REAL 泄漏进测试（既有测试已有此先例与注释）。

## Out of Scope

- **同一京东接口被包两遍**（一个死代码包装 + 一个真实路径）——另立规格。
- **订单「关闭」入口缺失**（状态词表有 CLOSED/CANCELLED/OUT_OF_STOCK，无任何 API）——另立规格。
- **批次作用域 / 一批一卡**——另立规格。
- **京东商品查询的批量化与跨运行缓存**——性能议题，另立规格。京东官方接口支持一次传最多 50 个商品编码而当前逐个串行（生产实测：同样 7 个编码在 11 秒内被重复查了 6 遍），确有优化空间；但本规格**明确不做**，且给后续规格留下一条前置约束：**任何缓存方案必须先保证瞬时失败的结论不被缓存**。
- **库存判定逻辑本身**——京东返回可用 0 就是 0，不在前端或后端「兜底」成可发。
- **1:N 换品**——frontend-audit-fixes 票 10。
- **471 的根因（我方签名时间戳/时钟）**——属运维域。本规格不修时钟，只要求这类故障**分类正确、可见、有告警**。当前三处时钟（本机 / 数据库容器 / Windows 宿主）实测同步，471 只在 08-25 出现过 4 次，是一次性漂移窗口——**但它随时可能再犯且当前无人察觉**，这正是要告警的原因。
- **阻断卡片的视觉与 PII 展示优化**——frontend-audit-fixes 票 09 已覆盖，见依赖关系。

## Further Notes

### 生产证据台账（可复核，只读）

生产库只读入口：`ssh zimupc "docker exec -i zimu-fulfillment-postgres-1 psql -U fulfillment -d fulfillment_hub -t -A"`（SQL 走 stdin）。**严禁任何写操作。**

| 结论 | 复核方式 |
|---|---|
| 门禁全史阻断 6 次、涉及 2 个发货批次 | `app.order_events` 中 `event_type_code='JD_SKU_MAPPING_CHECKED'` 且 `payload->>'gate_status'='BLOCKED'` 按 shipment 分组 |
| shipment 1 真因是 471 | `app.review_cases` id=2 的 `detail.affected_shipment_items` |
| 471 原文「时间戳已失效」 | `app.audit_logs` 中 `service='jd.isc' AND operation='queryGoodsInfo' AND business_code='471'`（id=54/60/70/72）的 `response_payload` |
| 471 之后 83 次调用全成功、门禁自愈 | 同表按 `business_code` 聚合；`skus` id=32 与 `provider_skus` id=32 的 `updated_at` 均不在事发窗口内 |
| shipment 17 真因是缺换算系数 + 运营被诱导补了冗余配置 | `review_cases` id=41 的 detail；`audit_logs` id=6461 → 6596 → 6598 的时间线 |
| 占位符单位暴露面 | `app.order_lines` 按 `unit_snapshot` 分组：「来源数量单位」15 / 件 10 / 份 6 / 袋 2 |
| 完整真相一直存在于幂等快照 | `app.idempotency_registry` 中 `scope='shipment.jd_sku_mapping.check'` 的 `response_snapshot->'body'`（4 条 BLOCKED 快照均含完整 issues） |
| 两条复核事项分属两个队列 | `review_cases` id=2/41 为 `SKU_OPS`，id=3/42/52 为 `FULFILLMENT_OPS` |
| 无映射的 31 个启用 SKU 及其建档时间 | `app.skus` LEFT JOIN `app.provider_skus`（provider_id=1, active） |
| 当前生产镜像已含 08-27 的透传修复 | 生产容器镜像 tag 对应的 commit 与 `ef37bea1` 的祖先关系 |

### 明确的未知（不用推断填充）

- **重试上限与退避的具体取值待校准。** 生产至今只观测到一次外部失败窗口（且是持续型的签名故障，非随机抖动），**没有可用于定参的失败分布数据**。规格给默认值并标注为待校准，不要把它包装成「基于数据的选择」。
- **京东业务码里哪些真正可重试，未知。** 生产只见过 471（不可重试）与 1000（成功）。可重试白名单起始为空，后续按真实观测扩充。
- **「34%」的正确分母未确定**，见就绪度视图一节。
- **`ef37bea1` 的逐项透传在生产零验证**——它写对了没有，只能靠本规格新增的测试和下一次真实阻断来确认。

### 一句话总结

这个门禁的判定逻辑基本是对的（它确实算出了 `JD_GOODS_QUERY_FAILED（471）`），坏的是**从判定到用户之间的那段路**：真相在幂等快照里完整保存，在事件里被压成计数，在阻断项出口被塌缩成一个码，在前端被渲染成裸码，最后还被派到了另一个岗位的队列里。本规格不重写判定，只把这段路修通。
