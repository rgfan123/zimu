# 企业微信消息接入、订单草稿与运单回传

Type: feature
Status: ready-for-agent

## Problem Statement

客户订单需求与第三方履约方的运单回传目前主要出现在普通个人微信群中，现有业务系统没有可靠、可审计的消息入口。普通微信群不能通过官方服务端 API 直接监听；如果把接收、模型识别、订单创建和运单写入绑在一个机器人流程中，会导致通道重试重复成单、识别错误直接污染业务事实、图片丢失后无法复核，以及未来更换模型或迁移到微信客服时需要重写业务链路。

一期需要让内部员工把普通微信群中的业务消息转发到一个指定企业微信业务群并 `@` API 模式智能机器人。机器人只回复“已接收”，系统在后台保存原始证据、异步识别意图、生成可编辑草稿并进入现有人工复核队列。任何订单或运单都必须经授权内部员工确认后才成为正式业务事实。

## Solution

在现有 Spring Boot、React 与 PostgreSQL 单体内增加一条薄的企业微信消息纵向切片，不建设独立 Gateway、LangBot 服务或消息中间件。

企业微信 Adapter 只负责官方回调协议、消息幂等、原始证据和固定回执。PostgreSQL 任务与 Spring Worker 异步完成媒体下载和消息解释。解释结果只产生 `MessageIntent`、`OrderDraft` 或 `ProviderTrackingDraft`，并为每个草稿创建一个 `ORDER_OPS` 的 `ReviewCase.OPEN`。现有人工复核工作台负责查看证据、修订字段、选择确定性映射候选并确认。确认订单时复用现有标准订单应用用例；确认运单时复用现有 Shipment/Tracking 应用用例。Adapter、模型和 MCP 均不得直接写业务表。

一期同时提供受限 MCP Adapter，供未来 Agent 查询证据、重跑解释和提交建议；MCP 不包含任何终局确认工具。是否允许 Agent 自动确认留待积累正确率数据后另行决策。

## User Stories

1. 作为订单运营人员，我希望把普通微信群中的客户需求转发到指定企微群，以便通过官方支持的通道进入业务系统。
2. 作为订单运营人员，我希望机器人只回复“已接收”，以免在群内暴露客户、地址、商品或运单信息。
3. 作为订单运营人员，我希望“已接收”只表示消息已安全保存，以免误认为订单已经创建或运单已经关联。
4. 作为系统管理员，我希望只有配置的企微业务群进入识别流程，以免其他群消息污染业务队列。
5. 作为群内企业成员，我希望无需额外人员白名单即可提交消息，以降低一期维护成本。
6. 作为审计人员，我希望保留企微消息 ID、会话、转发员工、原始内容和收到时间，以便还原证据链。
7. 作为审计人员，我希望原普通微信群发送人的昵称或描述只作为证据，不被伪装成稳定客户身份。
8. 作为系统管理员，我希望企微重复回调只落库和回执一次，以免通道重试产生重复草稿。
9. 作为订单运营人员，我希望不同消息 ID 的相同内容只提示疑似重复而不自动合并，以免真实重复下单被系统吞掉。
10. 作为订单运营人员，我希望一条 `@机器人` 消息默认形成一次提交，以免相邻群消息被错误拼接。
11. 作为订单运营人员，我希望通过系统草稿号补充内容，以便显式追加到已有提交；企微协议只给出引用内容时，该内容仅作为证据，不自动猜测父消息。
12. 作为订单运营人员，我希望图片原件被及时下载、解密并留存，以便始终能够对照原图复核。
13. 作为订单运营人员，我希望 OCR 或多模态结果与原件分离，以便更换模型后重新解释而不修改证据。
14. 作为订单运营人员，我希望图片或识别任务最终失败时出现一条人工待办，以免失败被静默忽略。
15. 作为订单运营人员，我希望临时失败自动重试三次，以免短暂网络问题立即占用人工处理。
16. 作为订单运营人员，我希望系统区分客户订单、履约方运单、改单、取消、非业务消息和无法判断消息，以便进入正确处理路径。
17. 作为订单运营人员，我希望明确的非业务消息只留档而不创建待办，以免人工队列充满闲聊。
18. 作为订单运营人员，我希望识别为客户订单后即使缺字段也立即进入复核，以免不完整需求隐藏在消息收件箱中。
19. 作为订单运营人员，我希望模型只提取原始客户、收货和商品描述，以免模型猜测内部 Customer 或 SKU。
20. 作为订单运营人员，我希望 Customer 和 SKU 只通过确定性映射生成候选，以便零命中和多命中都由人工决定。
21. 作为订单运营人员，我希望一期即使 Customer 和 SKU 唯一命中也仍需人工确认订单，以便在准确率未知时控制风险。
22. 作为订单运营人员，我希望首次确认客户后保存企微渠道身份绑定，以便后续自动带出客户候选。
23. 作为客户主数据管理员，我希望未匹配客户可在复核页选择已有客户或创建新客户，以便在一个工作流中完成建档。
24. 作为客户主数据管理员，我希望新客户编码由系统生成，以免模型或操作员制造不一致编码。
25. 作为订单运营人员，我希望同一客户与收货信息下的多个商品形成一个多行草稿，以符合实际订单结构。
26. 作为订单运营人员，我希望不同收货人或地址拆成独立草稿，以便分别复核和成单。
27. 作为订单运营人员，我希望来源单号由消息提交和草稿序号生成，以免依赖消息中不存在的单号。
28. 作为订单运营人员，我希望草稿缺少收货或结账字段时可以补充或选择已有资料，以便达到标准订单必填条件。
29. 作为订单运营人员，我希望必填字段未完整前不能确认成单，以免无效数据进入履约。
30. 作为履约运营人员，我希望 SKU 主数据决定履约方，以免模型按“猪肉”或“非牛羊肉”等名称猜测第三方履约方。
31. 作为履约运营人员，我希望当前猪肉等非牛羊肉商品通过 SKU 主数据显式归属第三方，以便未来调整范围时只维护主数据。
32. 作为订单运营人员，我希望改单或取消必须携带订单号或回复原下单消息，以便可靠定位目标订单。
33. 作为订单运营人员，我希望改单和取消只创建人工待办，以免消息直接修改或取消已确认订单。
34. 作为履约运营人员，我希望第三方可以逐行返回脱敏姓名和快递单号，以适配当前真实回传格式。
35. 作为履约运营人员，我希望一批回传中的每一行独立生成运单草稿，以便单行问题不阻塞其他运单。
36. 作为履约运营人员，我希望系统任务号成为最强关联键，以便明确绑定发货任务。
37. 作为履约运营人员，我希望没有任务号时可用带 `*` 的脱敏姓名在当前待回传第三方任务中做唯一匹配，以减少人工选择。
38. 作为履约运营人员，我希望零命中或多命中时必须人工选任务，以免按转发人、昵称或时间猜测。
39. 作为履约运营人员，我希望运单号前缀通过显式配置映射物流公司候选，例如 `SF` 对应顺丰，以便复用业务惯例而不依赖模型。
40. 作为履约运营人员，我希望物流公司前缀未命中、多命中或与消息冲突时人工选择，以免错误物流公司进入正式运单。
41. 作为履约运营人员，我希望只返回姓名和运单号时默认整项发货任务全部发出，以符合第三方约定。
42. 作为履约运营人员，我希望部分发货、缺货或异常必须明确说明并人工录入实际数量，以保留真实履约事实。
43. 作为履约运营人员，我希望企微回传不设置或推断实际发货时间，以免把消息时间冒充业务时间。
44. 作为履约运营人员，我希望系统仍记录运单接收时间和人工确认时间，以满足审计需要。
45. 作为履约运营人员，我希望批量勾选确认所有已通过校验的运单草稿，以提高批量处理效率。
46. 作为履约运营人员，我希望一行确认失败不回滚其他成功行，以便问题行继续单独处理。
47. 作为复核人员，我希望每个草稿只产生一个 `ORDER_OPS` 待办，以免客户、SKU 和缺字段问题造成待办爆炸。
48. 作为复核人员，我希望在同一页面查看原消息、原图、模型原值、映射候选、人工修改和最终确认，以便完整核对。
49. 作为审计人员，我希望保存模型供应商、模型名、提示词版本和每次解释结果，以便评估正确率和重放。
50. 作为系统管理员，我希望替换模型不影响消息接收、草稿、复核和成单逻辑，以降低供应商锁定。
51. 作为系统管理员，我希望任务积压和最终失败只在后台告警，以免群里产生不可控的补发消息。
52. 作为数据管理员，我希望订单和运单相关消息、图片沿用业务审计周期，以满足业务追溯。
53. 作为数据管理员，我希望非业务消息默认 30 天后清理且期限可配置，以控制无关数据占用。
54. 作为未来 Agent，我希望通过 MCP 查询消息、草稿、候选和复核事项，以便辅助人工处理。
55. 作为未来 Agent，我希望通过 MCP 触发重新识别、提交修改建议和补充证据，以便自动化非终局工作。
56. 作为业务负责人，我希望 MCP 不暴露成单、运单确认、关闭待办或取消订单工具，以便正确率达标前保留人工控制。

## Implementation Decisions

### 架构与模块

- 在现有单体内增加企业微信 Adapter、消息应用模块、解释 Adapter、复核用例扩展和 MCP Adapter；不新增独立部署服务。
- 企业微信 Adapter 只处理官方协议、业务群 allowlist、规范化、幂等保存、媒体任务创建与固定回执。它不得包含意图、订单、SKU、履约方或运单匹配规则。
- 消息应用模块拥有 `ChannelMessage`、`MessageMedia`、`MessageSubmission`、`MessageIntent`、`OrderDraft`、`ProviderTrackingDraft` 和 `ChannelIdentity`。
- `MessageInterpreter` 是唯一模型接缝。其输出是版本化派生结果，不能确认 Customer、SKU、Shipment 或 Tracking。
- 确认订单复用现有标准订单创建应用用例；确认运单复用现有 Shipment/Tracking 接收应用用例。不得通过内部 HTTP 自调用，也不得由 Adapter 直写业务表。
- 人工入口扩展现有复核工作台，不新建平行后台。

### 接收与异步执行

- 对外提供企业微信 URL 验证与加密消息回调 HTTP 接缝，连接配置通过服务端配置标识定位 Token、EncodingAESKey、企微主体和允许群，不把秘密放在 URL、数据库响应或日志中。
- 消息唯一键至少包含企微主体/机器人连接作用域与企微消息 ID，避免不同作用域的 ID 碰撞。
- 接收事务原子保存 `ChannelMessage`、必要的 `MessageSubmission` 与异步任务，然后返回固定文本“已接收”。回执不等待媒体下载或解释。
- PostgreSQL 任务表保存任务类型、载荷引用、状态、尝试次数、下次执行时间、租约、最后错误和时间戳。Worker 使用可恢复租约领取任务，最多尝试三次；进程重启后可继续处理。
- 同一提交的相同任务使用稳定幂等键；重试或并发 Worker 不得重复创建解释版本、草稿或 ReviewCase。
- 不引入 Kafka、RabbitMQ 或独立任务服务。Redis 不是该流程正确性的唯一存储。

### 数据模型

- 新增渠道消息、媒体、提交、解释版本、订单草稿/草稿行、运单草稿、渠道身份/Customer 绑定和异步任务持久化结构。
- `ChannelMessage` 保存规范化元数据、原始协议载荷引用、发送者、会话、消息类型、内容、协议提供的引用类型/内容和收到时间；当前智能机器人协议不提供稳定父消息 ID，系统不得按引用文字猜测回复关系。原普通微信群发送人信息只能进入证据字段。
- `MessageMedia` 保存渠道媒体标识、下载状态、受控文件引用、哈希、内容类型、大小、解密信息、失败原因和保留策略；原件不可变。
- `MessageInterpretation` 保存输入提交、解释版本、供应商、模型、提示词版本、结构化输出、意图、错误和创建时间；重跑追加版本，不覆盖历史。
- `OrderDraft` 保存提取原值、拆分来源、Customer/SKU 候选、缺失项、人工修订版本、确认人和确认时间。一个提交可以生成多个草稿。
- `ProviderTrackingDraft` 保存逐行原始姓名、运单号、物流公司候选、发货任务候选、数量判断、校验问题、确认人和确认时间。一个批量消息可以生成多个草稿。
- `ChannelIdentity` 的唯一作用域包含企微主体、接入类型和渠道标识。显示名、备注、描述和头像均保存为可变资料快照；`external_userid` 不命名或展示为“微信号”。
- `ReviewCase` 增加消息提交、订单草稿和运单草稿主体引用，并扩展“恰好一个主体”约束；正式订单前的草稿不得伪造 `order_id`。
- `ReviewCase.status=OPEN` 是人工待办的唯一权威状态。确认订单/运单时在同一事务关闭相应事项；拒绝草稿时使用 `DISMISSED` 并保存理由。
- 调整 Shipment 数据库约束与应用命令，使第三方企微回传确认后可以 `SHIPPED` 且 `shipped_at` 为空；`Tracking.received_at` 和复核解决时间分别表示运单接收与人工确认，不冒充实际发货时间。
- 物流公司前缀映射作为可维护的确定性配置，前缀归一化后必须恰好命中一个启用的 Carrier 才能形成候选。

### 意图与草稿规则

- 意图枚举固定为 `CUSTOMER_ORDER`、`SUPPLIER_TRACKING`、`ORDER_CHANGE`、`ORDER_CANCEL`、`NON_BUSINESS`、`NEED_REVIEW`。
- `CUSTOMER_ORDER`、`SUPPLIER_TRACKING` 和 `NEED_REVIEW` 创建开放复核事项；`ORDER_CHANGE`、`ORDER_CANCEL` 创建只允许人工处理的开放事项；`NON_BUSINESS` 不创建事项。
- 一条 `@机器人` 消息默认形成一个提交。只有提供系统草稿号，或未来通道明确提供稳定父消息 ID 时才能追加；当前企微引用类型/内容只作证据。禁止基于文字相似或时间窗口拼接。
- 客户与 SKU 映射只接受现有确定性映射的唯一候选。模型不得输出被视为已确认的内部 ID。
- 同一客户与收货快照下的商品形成多行订单草稿；不同收货人或地址拆分为多个草稿。每个草稿来源单号由消息提交标识和稳定草稿序号生成。
- 标准订单所有必填项完整前不可确认。商品展示字段以人工确认的 SKU 主数据为准，消息原始描述仍保留为证据。
- 第三方当前处理范围由 SKU 的 `FulfillmentProvider` 归属决定，不实现“非牛羊肉”字符串规则。
- 批量运单严格按逐行姓名—运单号解析。一行一个草稿；无法建立逐行对应关系时整体解释为 `NEED_REVIEW`，不得按两个列表的位置猜测。
- 发货任务匹配优先使用系统任务号。没有任务号时，脱敏姓名中的 `*` 作为零个或多个字符的通配符，仅在当前状态为待回传且履约方为第三方的任务中匹配收货人快照；只有恰好一条候选时可带出。
- 第三方仅返回姓名和运单号代表该任务全部指令数量已发；明确出现部分、缺货或异常时必须要求人工确认实际数量。
- 不从企微消息提取、默认或推断实际发货时间。

### 人工复核事务

- 每个订单草稿或运单草稿只创建一个 `ORDER_OPS` 的 `ReviewCase.OPEN`，所有缺失项和候选冲突放入该事项的结构化 detail。
- 订单复核支持查看证据、选择/创建 Customer、选择 SKU、补充收货与结账信息、修订数量、拒绝草稿和确认成单。
- 创建新 Customer 时系统生成客户编码；客户名称由人工确认。渠道身份绑定与 Customer 创建/选择在同一业务命令中完成。
- 确认订单命令要求幂等键、草稿期望版本、复核事项期望版本和操作员身份；单个事务创建 CanonicalOrder、记录证据引用、标记草稿已确认、解决 ReviewCase、写 OrderEvent/OrderVersion/AuditLog。
- 运单复核支持修订物流公司、发货任务与实际数量，并显示前缀和姓名匹配依据。
- 单条确认运单命令要求幂等键、草稿/事项期望版本和操作员身份；单个事务创建或更新 Shipment/Tracking 事实、标记草稿已确认、解决 ReviewCase 并写事件、版本和审计。
- 批量确认是若干独立单条命令的编排，返回逐行成功/失败结果；不得使用覆盖整批的单事务。
- 改单和取消事项只提供定位与人工处理入口，本规格不新增自动改单或自动取消命令。

### 公共 API 与页面

- 企业微信回调端点属于 Connector 接缝，不暴露业务写参数。
- 管理 API 提供消息提交详情、原始媒体受权访问、解释历史、订单草稿详情/修订/确认/拒绝、运单草稿详情/修订/单条确认/批量确认和重新解释命令。
- 所有写 API 延续现有幂等键、操作员身份、乐观版本与统一错误响应约定。
- ReviewCase 查询返回草稿主体类型、结构化检查项、允许动作和证据摘要；不向页面直接倾倒未知 JSON 字段。
- 复核页面对订单草稿和运单草稿使用专门的白名单视图模型，未知字段不直接渲染。
- 任务积压、最终失败和媒体失败在后台提供可筛选状态与告警摘要；不向原群补发消息。

### MCP 能力

- MCP 作为现有应用层的 Adapter，不拥有独立业务逻辑或数据库写入路径。
- 一期允许工具：查询消息提交、读取消息/媒体元数据、读取解释历史、查询订单草稿、查询运单草稿、查询候选、查询 ReviewCase、触发重新解释、提交草稿修改建议、提交补充材料、显式提交进入人工复核。
- 一期禁止注册：确认订单、确认运单、批量确认运单、解决/关闭/驳回复核、创建 Customer、绑定渠道身份、修改或取消订单等终局工具。
- MCP 写工具必须使用认证上下文中的 Agent 身份、幂等键、期望版本和 AuditLog；工具参数不得伪造 operator。
- 未来自动确认能力不在本规格中；需基于已留存的模型版本、人工修订和最终结果计算正确率后另开决策票。

### 安全、隐私与保留

- 企业微信 Token、EncodingAESKey、模型密钥和 MCP 凭据只通过秘密配置注入，不进入数据库明文字段、API 响应、审计 payload 或日志。
- 原始消息、客户身份、地址、电话、图片和模型输入输出按业务敏感数据处理；列表默认只展示必要摘要，详情需要后台授权。
- 订单与运单相关证据跟随业务审计保留策略；`NON_BUSINESS` 消息默认 30 天后清理，配置可以延长或缩短。
- 清理任务只删除达到期限且没有订单、运单、开放 ReviewCase 或审计保留引用的数据；清理操作本身记录审计摘要。

## Testing Decisions

- 测试只验证公共行为，不直接调用私有方法或直接写业务表冒充工作流。
- 第一条主验收接缝是企业微信回调 HTTP：使用固定的官方协议加密样本和测试密钥验证 URL 校验、验签解密、业务群过滤、幂等落库、固定“已接收”回执、任务创建和重复回调行为。
- 回调验收使用真实 PostgreSQL；企业微信网络、媒体下载和模型服务只在各自 Adapter 边界使用测试替身。
- Worker 验收覆盖成功、三次重试、租约超时恢复、并发领取、幂等重放、原图哈希留存、解释版本追加以及最终只创建一个 ReviewCase。
- 第二条主验收接缝是管理后台公共 API/UI：通过 HTTP 完成订单草稿编辑与确认，随后从订单查询验证 Customer、收货快照、多行 SKU、来源单号、ReviewCase 解决状态、事件、版本和审计。
- 运单 API 验收覆盖任务号匹配、脱敏姓名唯一/零/多命中、Carrier 前缀唯一/冲突、整项发货、部分发货、无实际发货时间和批量逐行成功/失败。
- 浏览器验收通过现有人工复核路由完成查看原图、修订、创建/选择客户、确认订单及批量确认运单；不得显示内部 JSON、秘密或未经翻译的字段。
- 第三条主验收接缝是 MCP 协议：验证工具发现、允许工具的认证/版本/幂等行为，并断言禁止的终局工具不在工具列表中。
- Schema smoke 验证新增外键、唯一键、ReviewCase 单主体约束、Tracking 唯一性、可空 `shipped_at` 以及 NON_BUSINESS 保留清理门禁。
- OpenAPI 与前端类型测试覆盖所有公共请求/响应枚举和错误；MCP 契约独立验证但复用相同应用用例。
- 正式可用门槛包含一次真实企微业务群验收：企业成员转发文字与图文并 `@` 机器人、群内只收到一次“已接收”、后台出现原始证据和草稿、人工确认后出现真实业务订单或运单。没有真实企微配置时，本地测试成功只能报告为实现证据，不能声称生产接入已验收。

## Out of Scope

- 普通个人微信群的非官方自动监听、注入、Hook 或客户端自动化。
- LangBot 插件、独立 WeCom Gateway、Kafka、RabbitMQ 或微服务拆分。
- 微信客服一期接入；领域模型和 Channel Adapter 接缝需允许后续替换入口。
- 模型训练、OCR 引擎研发、自动 Prompt 优化或 Agent 调度平台。
- Agent 自动确认订单、运单、客户、SKU 或关闭 ReviewCase。
- 根据昵称、转发人、群、时间窗口、近似文本或商品品类猜测业务身份。
- 自动执行已确认订单的改单或取消。
- 自动获取或存储客户所谓“真实微信号”；企微 `external_userid` 只作为作用域内渠道身份。
- 物流轨迹查询、签收/妥投判定和实际发货时间补全。
- 本规格中的生产部署、企微管理员配置、域名发布和真实密钥交付。

## Further Notes

- 当前普通微信群阶段只有转发员工和企微业务群是可验证传输身份，原发送人信息不能用于渠道身份绑定。迁移到“客户联系”或“微信客服”后，新的 Adapter 可以提供作用域内的 `external_userid` 和昵称等资料，但仍必须遵守显式 Customer 绑定规则。
- 当前项目的内容寻址文件存储一期可挂载持久化 Docker 卷。替换 MinIO/S3 时应保持受控文件引用与哈希语义，不改变消息和草稿模型。
- 当前 Shipment 约束要求 `SHIPPED` 时存在 `shipped_at`，与已确认业务约定冲突；实现票必须同时修改数据库、应用命令、查询 DTO 和验收，不能只在企微 Adapter 中填一个伪时间。
- 本规格已达到 `ready-for-agent`，但不代表已经实施、提交、部署或完成真实企微验收。
