# 01 — 允许已发货但实际发货时间未知

**What to build:** 让第三方运单确认能够表达“已确认发货，但没有可靠的实际发货时间”。现有运单接收、订单状态、查询和页面必须完整支持该事实，不能用消息时间、接收时间或确认时间填充 `shipped_at`。

**Blocked by:** None — can start immediately.

**Status:** resolved

- [x] 通过公共运单接收用例可以确认一笔第三方发货，并让 Shipment 进入 `SHIPPED`、Tracking 正常落库且实际发货时间为空。
- [x] 数据库约束允许上述合法状态，同时继续拒绝其他不一致的 Shipment 状态组合。
- [x] 运单接收时间和人工确认/审计时间仍分别可查询，且不会被展示或导出为实际发货时间。
- [x] 订单详情与履约页面在实际发货时间为空时展示“未提供”或等价用户文案，不报错、不显示伪日期。
- [x] 现有明确提供实际发货时间的 Excel/JD 路径保持兼容。
- [x] Schema smoke、公共 HTTP 验收、前端测试与全量回归覆盖有时间和无时间两种路径。

## Answer

第三方运单回传现在允许“已发货但实际发货时间未知”：Shipment 可进入 `SHIPPED` 且 `shipped_at` 保持 `NULL`，Tracking 接收时间和审计时间仍独立记录。数据库继续拒绝非发货状态携带发货时间；按实际发货日统计的渠道/商品视图会排除未知时间记录，不再用更新时间回填。订单详情和履约页面统一显示“未提供”，已有明确时间路径保持兼容。

Flyway V1 已冻结，V6 作为增量迁移放宽约束并重建分析视图。验证包括有/无发货时间公共 HTTP 用例、fresh PostgreSQL schema smoke、前端 22/22、后端全量 54 个测试（0 失败、0 错误、2 个外部样例条件跳过）、Java 21 镜像构建，以及从只读 V3 数据库克隆升级到 V7；克隆中 38 张既有业务表行数保持一致，源库未被迁移。
