# 06 — 处理不完整、多商品和多收货地址订单

**What to build:** 运营人员可以可靠处理不完整需求、一单多商品和一条消息多个收货地址，并通过系统草稿号补充既有草稿；未来通道若明确提供稳定父消息 ID，也可将其作为显式关联。系统提示疑似重复但不自动吞单或拼单。

**Blocked by:** 04 — 确认一条完整客户订单.

**Status:** ready-for-agent

- [ ] 一旦识别为客户订单，即使字段不完整也立即生成 OrderDraft 与一个 `ORDER_OPS / OPEN` ReviewCase，并列出缺失字段。
- [ ] 同一客户与收货信息下的多个商品生成一个多行草稿；不同收货人或地址生成分别复核的多个草稿并共同引用原始消息。
- [ ] 每个草稿使用消息提交标识和稳定草稿序号生成唯一 WECOM 来源单号。
- [ ] 后续消息只有携带有效草稿号，或通道明确提供稳定父消息 ID 时才追加到既有提交；当前企微引用类型/内容只作证据，系统不按文字或时间窗口合并消息。
- [ ] 不同消息 ID 的相同或近似内容分别生成草稿，并在复核页提示疑似重复而不自动合并、拒绝或删除。
- [ ] 复核人员可以补充/选择收货和结账资料并修订商品数量；商品名称、规格和单位以确认后的 SKU 主数据为准。
- [ ] 每个拆分草稿独立确认、拒绝和审计，一个草稿失败不影响同一消息产生的其他草稿。
- [ ] 公共 API 与浏览器验收覆盖缺字段、多商品、多地址、显式追加、非显式相邻消息和疑似重复。
