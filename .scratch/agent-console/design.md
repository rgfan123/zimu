# Agent 管理板块设计

Type: design
Status: confirmed（§9 三项已由用户裁定，见 §9）
日期：2026-08-19

## 0. 为什么现在做这个设计

后端 `meta-agent-platform-impl` 13 票已完成 9 张（01–09：三表落地、注册表切 DB、评测数据化、Runtime Adapter、四路径收敛、MCP 权限隔离、门禁引擎、QUALITY 链路）。**剩下的 10/11/12/13 正好是本板块要调用的 API**：

| 票 | 内容 | 本设计的依赖关系 |
|---|---|---|
| 10 | Meta-Agent 工具面（`list_agent_tools` + 定义写工具） | P6 对话建 Agent 的能力底座 |
| 11 | 异步任务基建 + 定义域写端点（202 / confirm / reject / set-enabled / rollback） | P2 的全部写动作 |
| 12 | 读端点 + `/internal` 只读镜像 | P1 / P2 / P3 / P5 的全部读 |
| 13 | Meta-Agent REST 端点（202 闭环） | P6 的提交与轮询 |

因此本设计**先于 11/12/13 实现**，目的是让 API 契约由真实界面需求塑形，而不是界面去迁就已定死的端点。§6 列出本设计对这三张票的具体契约要求。

## 1. 这个板块要回答的五个问题

设计不从页面出发，从"人来这里想知道什么"出发：

1. **现在有哪些 Agent，各自健康吗** → P1 列表
2. **这个 Agent 为什么这么答** → P3 运行记录 + P4 运行详情
3. **我要改它的行为，且改坏了能退回去** → P2 详情（版本链 + 草稿确认闭环）
4. **它答得好不好** → P5 评测
5. **我要新建一个 Agent，但我不会写提示词** → P6 对话式创建

## 2. 信息架构与路由

**归属：顶级板块「Agent 中心」**（用户裁定）。与工作台、订单中心、库存中心平级，不塞进系统管理——Agent 已经是这套系统的一等能力，不是一个配置项。

**路由与菜单层级严格一致**（不重复 `/system/jd-tools` 菜单挂 `/fulfillment/jd-*` 那种错位）：

| 页面 | 路由 | 菜单 |
|---|---|---|
| P1 Agent 列表 | `/agents` | 可见 |
| P3 运行记录 | `/agents/runs` | 可见 |
| P2 Agent 详情 | `/agents/:slug` | 隐藏（下钻） |
| P4 运行详情 | `/agents/runs/:runId` | 隐藏（下钻） |
| P5 评测 | `/agents/:slug/evals` | 隐藏（P2 内 tab） |
| P6 对话式创建 | `/agents/new` | 隐藏（P1 主操作；**后置，见 §9**） |

**已知债务（不在本板块单独解决）**：分组节点「Agent 中心」与叶子「Agent 列表」都落在 `/agents`，沿用既有菜单模型的 `~` 后缀区分机制。这个 hack 是 `repo-design-hardening` 票 18（GitHub #61）要全局清掉的，本板块不另建一套并行机制。

**所有详情走真实路由，不用本地状态抽屉**；筛选、分页、视图切换全部进 query string。这是本板块相对既有页面的硬性改进——`.scratch/repo-design-audit/findings.md` 第 10 条记录了全站只有订单详情一个动态路由、其余全靠 useState 驱动抽屉，导致无法分享链接、后退键失效、刷新丢失。Agent 中心从第一天就不背这个债。

## 3. 页面设计

### P1 Agent 列表 `/agents`

**一行一个 slug**（不是一行一个版本——版本链在详情里看）。

| 列 | 内容 | 设计要点 |
|---|---|---|
| Agent | 名称 + slug | slug 是身份键，等宽字体 |
| 运行状态 | 运行中 / 已停用 / 无生效版本 | **见 §4，这是本板块最容易做错的地方** |
| 当前版本 | v3 | 点击进版本链 |
| 待确认草稿 | 徽标「2 个待确认」 | 有草稿才显示，是主要的行动召唤 |
| 工具 | 白名单数量，悬停展开 | 数量为 0 时显示「无工具」而非空白 |
| 写权限 | 仅 `allow_write=true` 显示醒目标记 | 一期只有 meta-agent，**红线的可视化** |
| 近 7 日运行 | 迷你趋势 + 失败数 | 失败数非零时着色 |

主操作：**新建 Agent（对话式）** → P6。

筛选：运行状态、是否有待确认草稿、是否带写权限。全部进 URL。

### P2 Agent 详情 `/agents/:slug`

三个 tab：**当前生效 / 版本链 / 评测**（评测 tab 即 P5）。

**当前生效** 展示这一版定义的全部事实：名称、描述、系统提示词（长文本，可折叠，等宽）、提示词版本、模型引用、工具白名单（逐个列出，标注读/写属性）、输出 schema（JSON 折叠视图）、守卫豁免（空数组时显示「默认守卫全部生效」而不是空白）、确认人与确认时间。

**版本链** 是一条时间线：每个版本一个节点，标注 draft / active / retired，谁在什么时候确认的。**回滚不是回边**——按 03 决策「状态机无回边，回滚 = 复制成新草稿再确认」，所以版本链上的操作是「以此版本为蓝本创建草稿」，而不是「回滚到此版本」。UI 文案必须如实反映这一点，否则用户会以为点一下就回去了。

写动作（全部经 §5 的确认组件）：
- **确认草稿**（草稿 → active，同时确认该版本全部待确认评测用例——07 决策的联动）
- **拒绝草稿**
- **启用 / 停用**（改 `enabled`，与版本状态正交）
- **以此版本创建草稿**（回滚路径）

### P3 运行记录 `/agents/runs`

列表：run_id、Agent、状态（RUNNING / SUCCESS / FAILED）、outcome（SUCCESS / NEEDS_INPUT / REJECTED / FAILED）、耗时、token、关联业务实体、开始时间。

**LIVE 与 PREVIEW 必须视觉隔离**：默认只看 LIVE，PREVIEW（草稿试跑）要显式切换且带明显标识。`run_mode` 这个字段存在的全部理由就是防止草稿试跑污染对线上行为的判断——界面上把它们混在一列会让这个设计失效。

筛选：Agent、状态、outcome、run_mode、时间范围、业务实体。进 URL。

### P4 运行详情 `/agents/runs/:runId`

- 顶部：run 元信息 + 输入摘要（**只有 SHA-256 digest，没有原文**——这是 08 票的隐私设计，界面要如实说明「输入原文不留存，仅存摘要用于比对」，不要显示成空白让人以为丢数据了）
- 中部：**工具调用序列 Timeline**，每步显示工具名、序号、耗时、状态、参数与结果摘要（已脱敏）
- 底部：关联审计日志（同 run_id 双向可追溯）

失败时把 `error_type`（稳定枚举）放在最显眼处。

### P5 评测 `/agents/:slug/evals`

按版本分组展示用例，**INVARIANT 与 QUALITY 分两组**（确定性门禁 vs 有波动的质量评测，混在一起会让人误读基线）。

每条用例：case_key、metric_kind、输入、期望、状态（PENDING / CONFIRMED）。

**active 版本的用例只读**——07 决策「active 版本不可追加/修改，要加 = 新版本草稿」。UI 要在 active 版本上禁用「新增用例」并给出去处（「新增用例需先创建草稿版本」），而不是让按钮可点然后 422。

**人工纠正入口**（对应需求梳理里的「agent 决策有记忆」）：从复核结果一键生成 PENDING 用例——人工纠正天然就是「输入 + 期望输出」。这是记忆闭环的落点，落在评测而不是新开记忆表，避免与「审计只做流水不能当真源」的红线冲突。

### P6 对话式创建 `/agents/new`（后置）

Meta-Agent 对话。左侧对话流，右侧实时草稿预览。

用户说需求 → Meta-Agent 调 `list_agent_tools` 选工具 → 产出草稿（定义全量字段 + 建议评测用例）→ **落库为 draft，不启用**。

三种结局都要有对应呈现：
- **SUCCESS**：草稿预览 + 「去确认」跳 P2
- **NEEDS_INPUT**：澄清问题逐条列出，等用户补充
- **REJECTED**：明确说明拒绝理由（slug 冲突、要求写工具、企图改 meta-agent 自身等）

**红线的界面表达**：Meta-Agent 只能写草稿，启用永远是人工在 P2 做的。P6 里不能出现任何「创建并启用」的按钮。

## 4. 状态呈现：本板块最容易做错的地方

`status`（版本生命周期：draft / active / retired）与 `enabled`（运维启停）**正交**，运行条件是 `status='active' AND enabled=true`。

把两者合并成一个"状态"列是最自然也最错的做法。规则：

| status | enabled | 列表显示 | 含义 |
|---|---|---|---|
| active | true | **运行中** | 正常 |
| active | false | **已停用** | 有生效版本但被运维关掉 |
| 无 active 版本 | — | **无生效版本** | 只有草稿或全部 retired |
| draft | — | 不单独占行 | 作为 slug 行上的「待确认草稿」徽标 |

停用一个 Agent **不改变它的版本状态**，重新启用回到原版本——UI 文案要让这一点无歧义。

## 5. 危险动作的统一确认

确认草稿、拒绝草稿、启停、创建草稿都是有后果的动作，全部走同一个确认组件，且必须说清：

- **将发生什么**（确认草稿 v4 → v4 生效，当前 v3 转 retired）
- **影响范围**（该版本待确认评测用例 N 条将一并确认）
- **是否可逆**（版本状态机无回边；要退回需以旧版本为蓝本新建草稿再确认）

这与 `repo-design-hardening` 票 24（危险动作统一确认组件）是同一个组件，本板块应当直接复用而不是另起一套。若 24 尚未落地，本板块先建、24 再收编。

## 6. 本设计对后端 11 / 12 / 13 的契约要求

这是本设计最有价值的产出——**趁这三张票还没实现，把界面需要的东西提前提出来**：

**票 12（读端点）需要提供：**
1. Agent 列表要能一次拿到「slug + 当前 active 版本 + 待确认草稿数 + 近 7 日运行统计」，否则 P1 每行都要额外请求（N+1）
2. 版本链要能按 slug 拿到全部版本及其状态与确认信息
3. 运行记录列表必须支持按 `run_mode` 过滤，且**默认不返回 PREVIEW**
4. 工具白名单要带**读/写属性**（08 票已有该元数据），否则界面无法标注哪些是写工具
5. 模型元数据经服务端 allowlist 投影后可能是 `none`——响应要能区分「未命中 allowlist 故不公开」与「未配置」，界面文案不同

**票 11（写端点）需要提供：**
6. confirm / reject / set-enabled / rollback（= 以某版本创建草稿）四个动作，全部 202 异步 + 可轮询任务状态
7. confirm 必须原子地同时确认该版本的待确认评测用例（07 决策联动），部分成功要能回滚
8. 写动作要带版本号做乐观并发，防止两个人同时确认不同草稿

**票 13（Meta-Agent 端点）需要提供：**
9. 202 提交 + 轮询，响应要携带 `outcome`（SUCCESS / NEEDS_INPUT / REJECTED）与对应载荷
10. 拒绝要给出**结构化拒绝码**而非自由文本，界面才能给出可操作的下一步

## 7. 组件选型（沿用 09 票已 resolved 的结论）

- **P6 对话**：`@ant-design/x` 锁 1.6.x（MIT，peerDeps `antd ^5.20.3`，与项目 antd 5.21 零摩擦；2.x 需 antd 6，不升）。Bubble / Sender / Conversations / useXChat 覆盖对话式创建。
- **P1 / P3 / P5 列表与 P2 表单抽屉**：antd 原生 Table / Form / Descriptions / Tag / Timeline。草稿确认复刻已有的 `OrderDraftReviewPanel` 范式。
- **P4 工具调用序列**：antd Timeline；**近 7 日运行趋势**：echarts（项目已装）。
- 不引入 Langfuse 全套、不引入 shadcn/ui（Tailwind 体系冲突）、不引入已停更的 chat-ui-kit。

## 8. 不做什么

- **不做提示词在线编辑器的富文本化**——提示词是纯文本，等宽文本域足够；花哨编辑器会诱导人在界面里随手改高风险内容。
- **不在界面暴露 provider / model / api-key 的真实值**——红线：密钥绝不进 DB、日志、DTO；模型三元组经服务端 allowlist 投影。
- **不做 Agent 之间的编排/工作流画布**——`meta-agent-platform` 已明确排除低代码拖拽编排。
- **不做多租户与按人授权**——沿用既有单租户与 Basic Auth，权限体系是独立 effort。
- **一期不做运行中 HITL 挂起恢复**——04 决策已定，一期无此形态。

## 9. 已裁定事项（2026-08-19）

1. **归属**：顶级板块「Agent 中心」。已落入 §2。
2. **运行记录的位置**：**独立页做真源，详情页只放摘要 + 跳转**。
   - 理由：运行记录最主要的用法是「今天哪些跑挂了」——此时还不知道是哪个 Agent，做成详情内 tab 就得逐个点进去试；跨 Agent 排障是这张表存在的首要价值。
   - 既然筛选本来就进 URL，详情页里「该 Agent 的运行」不过是 `/agents/runs?agent=<slug>` 一个带参链接，**不需要第二套实现**。
   - P2 详情页内只保留「最近 5 次运行」摘要卡 + 「查看全部」跳转，不做完整表格。
   - 同类产品（Langfuse / Dify）均为全局运行列表 + 详情下钻，动线一致。
3. **P6 对话式创建：后置**。P1–P4 先做（依赖后端票 11、12），P5 次之，P6 最后（依赖后端票 10、13）。
