# MVP productization and operational acceptance

## Problem Statement

当前 MVP 已能演示主要页面和部分闭环，但仍存在待办只读、外部权限未证明、少量工程票留在 `need_review/claimed`、公开页面文案可能暴露 Mock/技术细节，以及端到端证据分散等问题。老板演示之后，需要把它收敛为能被运营人员稳定使用、能明确说明边界、能重复验收的本地成品。

## Solution

以人工复核、AI 演示订单、Excel 闭环、京东只读 SDK 和整栈验收为纵向切片，通过公共 HTTP、真实文件字节、浏览器路由和 Nginx 入口验证外部行为。保留不可控外部条件为显式 gate，不用 Mock 或合成数据替代真实权限证明。

## User Stories

1. 作为运营人员，我希望在人工复核工作台看到真实待办，以便按原因和责任团队处理。
2. 作为运营人员，我希望处理完成后关闭复核事项，并保留解决人、结论、版本和审计记录。
3. 作为运营人员，我希望不能自动关闭的客户/SKU 问题获得明确处理路径，以免系统猜测映射。
4. 作为演示人员，我希望在模拟下单页使用 AI 多轮提取草稿，人工确认后才产生 DEMO 订单。
5. 作为演示人员，我希望 AI 不可用时仍可使用固定场景，并看到诚实的能力说明。
6. 作为文件作业人员，我希望三种来源文件可导入、履约导出、运单回传并产生原格式回填文件。
7. 作为主数据管理员，我希望 SKU 映射资料只生成候选证据，未确认内容不自动落库。
8. 作为京东仓配操作员，我希望先以只读 SDK 查询仓库、出库单和轨迹，以便证明账号权限而不触发生产写操作。
9. 作为管理者，我希望所有 Mock、Demo、真实连接状态都被明确标识，以免被演示结果误导。
10. 作为交付责任人，我希望一条命令可重复验证业务 HTTP、Demo 隔离、文件闭环、Metabase 和重启幂等，以便判断当前构建是否可用。
11. 作为内部用户，我希望页面文案正式、易执行，不看到技术报错、测试占位或内部配置。

## Implementation Decisions

- ReviewCase 只能通过显式命令关闭，命令需要期望版本、解决类型和可审计备注；客户/SKU 映射仍使用现有主数据写 API，不在复核命令中猜测建档。
- AI 草稿属于 DEMO 上下文，只有明确确认后才转成 DemoRun；BUSINESS 列表、分析、审计默认窗口不得混入 DEMO。
- Excel 解析、导出和回填延续现有文件 HTTP seam，真实素材只用于验证，不将个人信息或样本数据纳入产物。
- 第三方部分发货后的续发必须由操作员通过 Fulfillment 的显式续发命令创建独立 Shipment/导出；命令按剩余量、乐观版本和幂等键校验，不允许测试直接写库冒充业务闭环。
- 京东真实联调默认仅读；生产 Token 与 UAT Token 不混用；账号、事业部和青龙业主号作为不同概念管理。
- Public-ready 先交付对账表，本票不自动改动用户文案；用户确认后再开修复票。
- 不提交、推送、发布或部署；本轮交付是本地工作树和本地验收证据。

## Testing Decisions

- 业务命令从公共 HTTP API 验证响应、后续查询可见性、冲突和隔离，不测私有方法。
- 文件闭环通过 multipart HTTP 与下载字节验证 XLSX/CSV 格式、编码、血缘和敏感信息清理。
- 前端使用纯变换测试保护导航/统计口径，并用真实浏览器验证关键路由和用户操作。
- 外部 API 仅在 SDK 边界 Mock；真实京东探针显式运行且限定只读。
- 最终使用全量 Maven/Vitest/build、Compose 公共 Nginx HTTP 和浏览器证据统一评价。
- Public Ready 红项必须拆成可执行整改票；原始错误、PII、Mock payload 和固定操作人不得作为“仅文案问题”留到发布后。
- 身份体系若尚未接入，必须作为 release gate 明确阻止正式发布，不能用浏览器可伪造的固定操作人代替。

## Out of Scope

- 未经明确授权的京东创建/取消出库单真实调用。
- 采购部门内部流程、企业微信机器人部署和生产域名发布。
- 将未确认的映射资料批量写入生产主数据。

## Further Notes

当真实凭据或第三方样例不可获得时，验收必须报告准确 gate，不得使用 Mock 成功替代外部证明。
