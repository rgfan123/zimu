# PostgreSQL native enum vs `varchar + CHECK`：事实核验

核验日期：2026-08-11。范围限于 PostgreSQL 18、pgJDBC 42.7.10 源码/当前文档、Hibernate ORM 7.2、Flyway 当前文档和 Metabase 官方文档/官方 issue。当前仓库尚无 `pom.xml`/Gradle 构建文件，因此未锁定实际 Hibernate、pgJDBC、Flyway、Metabase 版本，也未做项目运行时验证。

## 结论表

| 主张 | 判定 | 核验结论与限定 |
|---|---|---|
| PostgreSQL enum 的 `ORDER BY` 按定义顺序 | **Confirmed** | PostgreSQL 明确规定 enum 顺序是创建时列出的顺序，并支持标准比较、`ORDER BY`、`MIN`/`MAX`。但它只给出一个**全序**；分支状态机未必存在单一业务顺序，`order_event.type` 也没有天然的生命周期顺序。[PostgreSQL enum ordering](https://www.postgresql.org/docs/current/datatype-enum.html#DATATYPE-ENUM-ORDERING) |
| enum 查询中把 `'SHIPPED'` 写成 `'SHIPED'` 会报错 | **Confirmed, with parameter qualification** | 对 SQL 中的未定型字符串 literal，操作符解析会依据另一侧 enum 列确定类型；非法 label 会进入 enum 输入校验并报 `invalid input value for enum`。但 JDBC `setString()` 默认传的是 `varchar`，此时更可能先报 `enum = character varying`/列类型不匹配，而不是非法 label。[operator type resolution](https://www.postgresql.org/docs/current/typeconv-oper.html)；[enum type safety](https://www.postgresql.org/docs/current/datatype-enum.html#DATATYPE-ENUM-TYPE-SAFETY) |
| `varchar + CHECK` 查询拼错值会静默返回 0 行 | **Confirmed** | `CHECK` 约束约束的是写入/修改的行；普通 `WHERE status = 'SHIPED'` 只是合法的 varchar 比较，不触发约束，因此通常返回 0 行。这个对比确实是 native enum 在手写 SQL literal 上的额外保护。[PostgreSQL constraints](https://www.postgresql.org/docs/current/ddl-constraints.html#DDL-CONSTRAINTS-CHECK-CONSTRAINTS) |
| pgJDBC 用字符串绑定 enum 会报类型错误，需要 cast 或 `stringtype=unspecified` | **Confirmed, but not universal** | pgJDBC 文档确认 `setString()` 默认按 `VARCHAR` 发送；`stringtype=unspecified` 才按未定型值发送，让服务器推断 enum。42.7.10 源码也显示 `setString()` 选择 VARCHAR/UNSPECIFIED；`PGobject` 可携带具体 PostgreSQL 类型名并按该 OID 绑定。因此 cast、`stringtype=unspecified`、typed `PGobject`/ORM enum binder 都是路径，不能概括成“使用 native enum 就必然要在所有 SQL 中 CAST”。[`stringtype` docs](https://jdbc.postgresql.org/documentation/use/#connection-parameters)；[`PgPreparedStatement` 42.7.10 source](https://github.com/pgjdbc/pgjdbc/blob/REL42.7.10/pgjdbc/src/main/java/org/postgresql/jdbc/PgPreparedStatement.java#L388-L405)；[`PGobject` docs](https://jdbc.postgresql.org/documentation/publicapi/org/postgresql/util/PGobject.html) |
| JPA/Java enum 已经提供编译期类型安全 | **Qualified** | `OrderStatus.SHIPPED` 这类 Java 常量拼错会编译失败；但该保护不覆盖 native SQL 字符串、Flyway/seed SQL、Metabase 或外部文本输入。Hibernate 7.2 默认把 `@Enumerated(STRING)` 映射为 `VARCHAR + CHECK`；要使用 PostgreSQL named enum，需要 `@JdbcTypeCode(SqlTypes.NAMED_ENUM)` 或启用 `hibernate.type.prefer_native_enum_types`。[Hibernate 7.2 guide, Named enumerated types](https://docs.jboss.org/hibernate/orm/7.2/introduction/pdf/Hibernate_Introduction.pdf#page=34) |
| PostgreSQL 12+ 允许在事务里 `ALTER TYPE ... ADD VALUE`，但同事务不能使用新值 | **Confirmed** | 当前 PostgreSQL 明确说明：在事务块内添加的值，必须等事务提交后才能使用。PostgreSQL 11 文档仍禁止在事务块内执行，PostgreSQL 12 文档已经是当前语义，所以“PG 12 之后”的版本边界准确。[current `ALTER TYPE`](https://www.postgresql.org/docs/current/sql-altertype.html#SQL-ALTERTYPE-NOTES)；[PostgreSQL 11](https://www.postgresql.org/docs/11/sql-altertype.html)；[PostgreSQL 12](https://www.postgresql.org/docs/12/sql-altertype.html) |
| PostgreSQL enum 没有 `DROP VALUE` | **Confirmed** | 官方文档明确说已有 enum 值不能移除，除非删除并重建 enum 类型；可用的是 `ADD VALUE` 与 `RENAME VALUE`。[enum implementation details](https://www.postgresql.org/docs/current/datatype-enum.html#DATATYPE-ENUM-IMPLEMENTATION-DETAILS) |
| Flyway 默认每个 migration 一个事务 | **Confirmed, configurable** | Flyway 默认把每个 migration script 包在单独事务里；`group=true` 可把所有待执行 migrations 合并为一个事务；也可为 SQL migration 设置 `executeInTransaction=false`。[Flyway transaction handling](https://documentation.red-gate.com/fd/migration-transaction-handling-273973399.html)；[script configuration](https://documentation.red-gate.com/flyway/reference/script-configuration) |
| “加 enum 值并 UPDATE 存量数据必须拆两个 Flyway 版本” | **Qualified, wording too strong** | 在 PostgreSQL 12+ 与 Flyway 默认配置下，同一个 transactional migration 内 `ADD VALUE` 后立即 `UPDATE` 使用新值会失败，拆成两个 migrations 是常规解决方案。但并非唯一方案：可把脚本设为 `executeInTransaction=false`（代价是失去该脚本原子性）。若 `group=true`，即便拆成两个文件也可能仍在同一事务中，需额外处理。[PostgreSQL note](https://www.postgresql.org/docs/current/sql-altertype.html#SQL-ALTERTYPE-NOTES)；[Flyway `executeInTransaction`](https://documentation.red-gate.com/fd/flyway-execute-in-transaction-setting-277578997.html) |
| analytics 视图和 seed SQL 是 enum 最难用的地方 | **Qualified** | 静态 SQL literal（如 `WHERE status = 'SHIPPED'`）可由 PostgreSQL 推断为 enum，通常不需要 cast；真正容易遇到类型冲突的是由 pgJDBC/BI 工具按 `varchar` 绑定的参数。seed 中新增 enum 值并在同事务使用则确有迁移限制。因此“所有 analytics 原生 SQL 都添堵”过度概括。[PostgreSQL operator resolution](https://www.postgresql.org/docs/current/typeconv-oper.html)；[pgJDBC `stringtype`](https://jdbc.postgresql.org/documentation/use/#connection-parameters) |
| Metabase 对 PostgreSQL enum 的筛选下拉不如 text | **Unverified as a current general claim** | Metabase 官方文档说明下拉取决于字段 metadata、Category 语义与字段值扫描，没有给出“enum 一般不如 text”的保证或比较。官方 issue 证明 Metabase 0.53.6 的 model/saved-question enum filter 曾产生 `enum = character varying`，但这不足以证明当前版本或普通表筛选仍普遍如此；必须锁定项目 Metabase 版本并做 smoke test。[Metabase filter metadata](https://www.metabase.com/docs/latest/data-modeling/metadata-editing#filtering-on-this-field)；[official issue #55124](https://github.com/metabase/metabase/issues/55124) |

## 对当前 Q2 / Q23 的适用性

- 当前 [`数据库 Schema 设计`](../../wayfinder/tickets/db-schema-design.md) 的 Q2 已选择 PG native enum，但同一条明确把 `order_event.type` 标成“是否继续用 PG enum 待后续决策”。所以用户粘贴的 Claude 论证**主体属于 Q2 的通用存储形态争论，也覆盖了 Q23，但不等同于 Q23 本身**。
- 对 Q2 中的状态列：排序和非法 literal 校验是真实收益；迁移、JDBC/ORM 映射也是真实成本。不过本项目 `OrderStatus` 有主线和多条异常分支，`ShippingProgress` 与 `PendingStage` 又被拆成两轴，不能仅凭 `ORDER BY enum_column` 就声称得到完整业务顺序。若分析需要明确顺序，仍应在查询/视图中定义业务 `CASE` 或独立排序权重。
- 对 Q23 的 `order_event.type`：`ORDER_RECEIVED`、`SKU_MAPPED`、`JD_SHIPPED`、`SOURCE_SYNCED` 等是事件类别，时间线应按 `created_at`/序号排序，而不是按事件类型排序；因此“enum 自带业务顺序”对 Q23 基本不构成收益。真正相关的是：事件类型是否仍在快速扩展、希望数据库如何拒绝未知事件、Hibernate/native SQL/Metabase 的实际访问路径。
- `order_event.type` 已被 Q2 单独留待裁决，说明 Q23 可以只判断这一列，不必重开已经确认的所有状态列；若要把“五维状态一并改成 CHECK”，那是重新打开 Q2，而不是回答 Q23。
- 在项目依赖版本尚未锁定前，Hibernate 和 Metabase 部分只能作为实现风险，不应冒充本项目已复现事实。落地前最小验证应覆盖：Hibernate named-enum 持久化与查询、native query String 参数、Flyway `ADD VALUE` 迁移，以及确定版本的 Metabase table/model filter。
