# P0 表格接入、履约导出与运单回填规范

状态：Reviewed / Approved
日期：2026-08-11
权威边界：`wayfinder/tickets/p0-excel-closed-loop.md`、`wayfinder/tickets/db-schema-design.md` Q1–Q53

## 1. 目标与边界

P0 只闭环以下文件流程：

1. 彩食鲜、聚福宝、飞象来源表格进入系统；
2. 原文件、原始行和单元格长期留存，转换为唯一的 CanonicalOrder；
3. 按 SKU 已维护的唯一 FulfillmentProvider，分别生成京东官方导单文件或统一第三方发货指令文件；
4. 接收京东/第三方返回的实际发货数量、快递公司和运单号；
5. 按三平台原格式生成来源回填文件。

文件 Adapter 必须调用与未来 API Connector 相同的应用层用例，禁止直接写业务表。未来京东 SDK、三平台 API、MCP 和企业微信机器人不改变本规范中的 CanonicalOrder、Fulfillment、Shipment/Tracking 与 ReviewCase 规则。

P0 不包含：企业微信机器人真实发送、客户签收回调、物流轨迹、第三方库存管理、库存预占、静态礼包 BOM、仅根据姓名或仅根据电话猜测客户主数据。

## 2. 不可变原则

- CanonicalOrder 是长期事实源；任何导出文件都只是版本化派生物。
- 数量使用 `NUMERIC(18,3)` / BigDecimal，禁止浮点数；超过三位小数进入 `NEED_REVIEW`。
- 来源渠道、SKU、履约方和快递公司使用显式映射；来源订单客户以规范化后的姓名与手机号二元组确定性复用或自动创建，缺少任一字段才进入 `NEED_REVIEW`。
- 同一来源行不因商品、收货人或数量相同而合并；始终保留原 Sheet、原行号和原值。
- 文件名只作审计信息，格式识别依赖文件真实容器与表头指纹。
- 所有版本只追加，不覆盖历史文件。
- BUSINESS 与 DEMO 强隔离；DEMO 不得生成可交付业务文件。

## 3. 文件格式与渠道识别

### 3.1 识别顺序

1. 读取文件魔数：`PK` 表示 ZIP/OOXML，应按 XLSX 解析；不得只看扩展名。
2. 只读取候选表头，不使用订单数据内容判断渠道。
3. 表头仅做 Unicode NFKC、去 BOM、去首尾空白/制表符；不做同义词或模糊匹配。
4. 必须恰好命中一个表头指纹；零命中、多命中、重复关键表头或格式读取失败均进入 `NEED_REVIEW`。
5. 允许列重排和额外列；关键列缺失时禁止降级猜测。

### 3.2 专属表头指纹

| 格式 | 必须同时存在的表头 |
|---|---|
| 彩食鲜 | `主订单编号`、`子订单编号`、`供应商编码`、`站点编码`、`商品编号`、`下单数量` |
| 聚福宝 | `主单号`、`拆单号`、`供货商`、`渠道订单号`、`结算方式`、`需结算总额` |
| 飞象 v1（历史误命名 XLSX） | `订单号`、`订单商品ID`、`可发货数量`、`物流状态`、`物流公司`、`物流单号` |
| 飞象 v2（平台原始 CSV） | `订单号`、`订单商品ID`、`商品数量`、`物流状态`、`物流单号`、`收货人手机号` |
| 第三方履约输出模板（非来源） | 标题含`发货清单`，表头含`品名`、`数量`、`规格`、`收件人`、`电话`、`地址`、`发单人`、`备注` |

### 3.3 有效数据区

- 彩食鲜：Sheet `0`，第 1 行表头，第 2 行起逐行处理；空行跳过。
- 聚福宝：`sheet1`，第 1 行表头；清理每格尾随制表符；遇到`供应商汇总`或`汇总`区即停止解析。
- 飞象：优先支持平台原始真 CSV v2；当前实样为无 BOM、GBK/GB18030 兼容编码、逗号分隔、LF 换行、40 列。历史 `批量发货1786435269.csv` 实际是误命名 XLSX，只作为 v1 兼容输入，不得决定真 CSV 的输出编码或列结构。

## 4. 来源字段映射

### 4.1 彩食鲜

| 来源列 | 内部含义 | 规则 |
|---|---|---|
| `主订单编号` | source order reference | 有值时使用 |
| `子订单编号` | source line reference | 有值时使用；不得当内部订单号或出库单号 |
| `供应商编码` / `站点编码` | 来源上下文 | 原值快照 |
| `收货人` / `联系电话` | Receiver | 手机按文本保存 |
| `省` / `市` / `区` / `详细地址` | Receiver address | 同时保存分段原值和拼接完整地址 |
| `商品编号` / `商品名称` | source product reference/snapshot | 只用于显式 SKU 映射和人工候选 |
| `下单数量` | requested quantity | 必须大于 0 |
| `订单备注` | source remark | 原值快照 |
| `发货数量` / `物流公司代码` / `物流单号` / `错误原因` | 来源回填列 | 仅由 SourceReturn Adapter 修改 |

### 4.2 聚福宝

| 来源列 | 内部含义 | 规则 |
|---|---|---|
| `主单号` | source order reference | 去除尾随制表符 |
| `拆单号` | source line/reference | 去除尾随制表符 |
| `下单时间` | source ordered at | 按 Asia/Shanghai 解析，原值同时保留 |
| `收货人姓名` / `收货人电话` / `收货地址` | Receiver | 电话按文本保存 |
| `商品名称` / `商品ID` / `商品编码` / `商品条码` | source product reference/snapshot | 只允许命中显式来源 SKU 映射 |
| `数量` | requested quantity | 必须大于 0 |
| `订单备注` | source remark | 原值快照 |
| `是否发完` / `发货数量` / `快递公司` / `快递单号` | 来源回填列 | 仅由 SourceReturn Adapter 修改 |

### 4.3 飞象

| 来源列 | 内部含义 | 规则 |
|---|---|---|
| `订单号` | source order reference | 必填 |
| `会员名称` | customer snapshot | 不按名称单字段合并；必须与手机号组成二元身份 |
| `商品名称` / `商品ID` / `订单商品ID` | source product reference/snapshot | 只允许命中显式来源 SKU 映射 |
| v2 `商品数量` / v1 `可发货数量` | requested quantity | 按已唯一识别的模板版本取值，必须大于 0 |
| `收货人姓名` / `收货人手机号` / `收货人地址` | Receiver | 手机按文本保存 |
| `下单时间` | source ordered at | 按 Asia/Shanghai 解析，原值同时保留 |
| `物流状态` / `物流单号` | v2 来源回填列 | 正常回填为`已发货`、实际单号；v2 没有`物流公司`列，禁止擅自增列 |
| `物流状态` / `物流公司` / `物流单号` | v1 兼容回填列 | 仅用于历史 21 列误命名 XLSX 的兼容输出 |

## 5. 导入、分组与幂等

- 上传人必须选择 `NEW` 或 `REVISION`；REVISION 明确关联父批次。
- 完全相同文件以内容哈希和作用域返回已有结果；不得创建重复订单。
- 有来源主/子单号时使用明确来源标识。
- 缺来源编号时，只在同一 import batch、同一 Sheet 内，把连续且 Receiver 姓名、电话、完整地址完全一致的行组成一个 CanonicalOrder；不得跨 Sheet 或文件合并。
- 原文件先整体留痕，随后逐行容错。有效行继续，问题行进入 ReviewCase，不阻塞其他独立行。
- 每个来源订单文件形成一个 ImportBatch；识别完成后由操作员对整个批次执行一次确认，不逐行或逐客户确认。确认不是新状态，仍有 SKU、格式或数据质量阻断时拒绝确认；确认成功后才生成该批次的履约导出。
- 一个来源 ImportBatch 最终只生成一份按该来源原模板回填的完整结果文件；批次可包含多张内部订单和多个 Shipment，但必须在这些 Shipment 的运单结果全部回收后统一生成，不按客户或订单拆分来源回填。
- 订单行进入任一已生成履约文件后冻结履约字段；后续修订走人工取消、补发或纠正单。

## 6. SKU、礼包与数量换算

### 6.1 普通 SKU

只有命中 `source_channel_skus` 显式映射才能自动履约：

`京东出库数量 = 来源订单数量 × 映射乘数`

映射乘数缺失、为 0、非正数或格式非法时进入 `NEED_REVIEW`，禁止默认按 1 处理。

`source_channel_skus.quantity_multiplier` 保存当前映射乘数；普通 OrderLine 同时快照来源数量与本次乘数，并约束二者乘积等于 `requested_quantity`，保证后续修改映射不改写历史。

来源行自带 JD 编码时：

- 与维护映射一致：使用维护映射的 JD 编码和乘数；
- 与维护映射不一致：进入 `NEED_REVIEW`，两边都不静默覆盖；
- 只有 JD 编码但没有有效乘数：进入 `NEED_REVIEW`。

两条来源行即使收货人、商品和数量相同也分别换算并保留血缘，不合并为一条来源行。

### 6.2 当单定制礼包

礼包清单由其他部门按订单明确传入，不维护 SKU 主数据上的静态 BOM。每单保存不可变组件快照：

`组件导出数量 = 礼包份数 × 本单组件每份数量`

礼包只能由同一 FulfillmentProvider 的组件组成；跨履约方、缺组件映射或无法形成完整礼包份数进入 `NEED_REVIEW`。导出时组件带同一礼包分组标识并要求同盒发出。

### 6.3 京东整数约束

京东模板要求`*商品的出库数量`为正整数。换算结果不是正整数时进入 `NEED_REVIEW`，禁止四舍五入或截断。

## 7. 履约拆分与出库单号

- 一条 OrderLine 一期固定一个 FulfillmentProvider，发货过程中不改换。
- 同一 CanonicalOrder、同一 FulfillmentProvider、同一 Receiver 地址、同一发货批次合并为一个 Shipment，共用一个 `outbound_order_no` 和一个 Tracking。
- 不同 FulfillmentProvider 必须分别生成文件。
- 缺货形成后续批次时，使用新的 Shipment、出库单号和运单号。
- `outbound_order_no` 由系统生成并持久化；同一幂等请求重放返回原编号，不重新生成。

## 8. 京东官方模板输出

### 8.1 模板约束

- 使用真实 `JD冷链导单.xlsx` 的77列表头与顺序作为 golden template；不得自行删列或改名。
- 只在`导入数据`写有效商品行；禁止生成只有常量、没有收货人或商品的空壳行。
- 手机、来源订单号、出库单号、SKU 编码和运单号都按文本写入，避免科学计数法。
- 不解析地址；`*收货人地址`写完整地址。省/市/县有可信分段原值时可原样写入，否则留空。
- 货到付款不在 P0 范围；COD 且无可信金额时进入 `COD_AMOUNT_REQUIRED`。

### 8.2 固定值

| 京东列 | 固定值 |
|---|---|
| `*ISV来源编号` | `ISV0020000000079` |
| `*事业部编号` | `EBU4418056064528` |
| `*店铺编号` | `ESP0020008943717` |
| `青龙业主号` | `010K5064550` |
| `*仓库编号` | `118085840` |
| `*承运商编号` | `CYS0000010` |
| `*授权码pin` | `京诚乾元01` |
| `*销售平台来源` | 数值 `6` |

| `*商品金额` | 数值 `0`，不可为空 |

### 8.3 动态值

| 京东列 | 来源 |
|---|---|
| `*isv出库单号` | 持久化 `outbound_order_no`；同一 Shipment 所有商品行相同 |
| `销售平台订单号` | 来源订单号；缺失时留空，不伪造外部编号 |
| `销售平台下单时间` | 可解析的来源下单时间 |
| `*收货人姓名` / `*收货人手机` | Receiver 快照 |

| `*收货人地址` | 完整地址快照 |
| `客户留言` / `商家留言` | 来源备注或内部发货备注 |
| `*京东商品编号` | 已确认的 JD/EMG 映射 |
| `*商家商品编号` | 仅在已维护时填写，否则留空 |
| `*商品的出库数量` | 普通 SKU 或礼包组件换算后的本批正整数数量 |
| `采购单号` | 有明确采购单快照时填写 |

其他字段默认留空，不复制样例中的脏值或占位值。

## 9. 第三方履约文件

第三方没有外部模板限制，P0 使用统一 XLSX；一份文件只属于一个 FulfillmentProvider。`发货清单.xlsx` 的收货与商品列作为视觉基础，但系统模板必须加入稳定行定位和回传列。

精确列顺序：

1. `导出批次号`
2. `出库单号`
3. `导出明细号`
4. `履约方编码`
5. `履约方名称`
6. `内部订单号`
7. `来源渠道`
8. `来源订单号`
9. `订单行号`
10. `礼包分组标识`
11. `收件人`
12. `电话`
13. `地址`
14. `履约方SKU编码`
15. `品名`
16. `规格`
17. `单位`
18. `请求发货数量`
19. `结果`
20. `实际发货数量`
21. `快递公司`
22. `物流单号`
23. `发货时间`
24. `异常原因`

`导出批次号 + 导出明细号`必须唯一并确定性回指 `fulfillment_export_items.export_line_no`；礼包组件共享`礼包分组标识`，每行写对应 `provider_sku_code`。系统生成发货指令时，19–24列留空；第三方只能填写这些回传列，不得修改前18列。回传时允许 `SHIPPED`、`PARTIAL`、`FAILED`，其中“发货时间”可留空以表示履约方未提供可靠的实际发货时间，已提供时仍必须符合 `yyyy-MM-dd HH:mm:ss`。整份文件先校验后在单事务接收；结构或关联错误整批拒绝，合法的 PARTIAL/FAILED 不属于结构错误。

礼包回传按完整份数校验：同一礼包分组的全部组件必须使用同一 Shipment/Tracking，且每个组件 `实际发货数量 ÷ quantity_per_bundle` 必须得到相同的正整数礼包份数；缺组件、比例不一致或散件结果整批关联校验失败并进入人工复核，不得把散件累计为已发礼包。

## 10. Tracking 接收与来源回填

### 10.1 快递公司映射

映射保存在 `connector_configs.config.carrier_mappings`，通过应用层维护并写 Audit Log。首批内置：

| 内部承运商 | 彩食鲜 | 聚福宝 | 飞象 |
|---|---|---|---|
| 京东物流 | `JD` | `京东物流` | `京东物流` |

未命中映射时创建 `CARRIER_MAPPING` ReviewCase，人工确认一次后保存复用；禁止根据名称相似度或运单号前缀猜测。

### 10.2 单 Shipment 自动回填

| 来源 | 自动写入 |
|---|---|
| 彩食鲜 | `发货数量=实际实发数量`；`物流公司代码=渠道映射值`；`物流单号=Tracking`；无错误时`错误原因`留空 |
| 聚福宝 | `是否发完=是`；`发货数量=实际实发数量`；`快递公司=渠道映射值`；`快递单号=Tracking` |
| 飞象 v2 | `物流状态=已发货`；`物流单号=Tracking`；不存在的`物流公司`列不得新增 |
| 飞象 v1 | `物流状态=已发货`；`物流公司=渠道映射值`；`物流单号=Tracking` |

阶段性 SourceReturnExport 复制原文件结构和原行序，只填已有合法 Tracking 的行；未就绪行保持原值/空白。每一版永久保留。

### 10.3 多 Shipment 统一人工路径

同一来源商品行产生多个 Shipment 时：

1. 首个 Shipment 已知不能覆盖请求量或后来出现第二个 Shipment 时，自动回填只写该 OrderLine/Fulfillment 关联 Shipment 中 `shipment_sequence` 最小的首批快递公司和运单号，禁止硬编码全局 sequence=1；
2. 不复制来源行，不拼接多个运单，不用后续运单覆盖首批；
3. 创建 `MULTI_SHIPMENT_SOURCE_FOLLOWUP` ReviewCase；采购或后续履约仍进行时保留 `PROCUREMENT_IN_PROGRESS`/`WAITING_PROVIDER`，由开放 ReviewCase 表达人工责任；
4. 后续 Shipment/Tracking 全部保存在内部；
5. 管理后台按批次展示实发数量、履约方、出库单号、快递公司、运单号、实际发货时间和回传时间；未提供实际发货时间时显示“未提供”，不用回传或确认时间代替；
6. 全部真实 Shipment 已有 Tracking 且 Fulfillment 终局后，OrderLine 转 `NEED_REVIEW`；人工在来源平台完成后续处理后填写备注并点击“已完成后续回传”，系统再次验证上述终局条件，同一事务记录处理人/时间、关闭 ReviewCase、写 `MANUAL_SOURCE_FOLLOWUP_COMPLETED` OrderEvent/OrderVersion/Audit Log 并推进至 `COMPLETED`；不要求再次上传文件，也不得生成只含首批的 `is_final=true` 文件。

### 10.4 飞象 CSV 强制门禁

飞象最终产物必须是真实文本 CSV：

- 使用 CSV serializer，禁止 XLSX exporter 后只改扩展名；
- 文件名以`.csv`结尾；
- 内容不得以`PK`开头；
- v2 精确保留原40列及顺序，只修改实样存在的`物流状态`、`物流单号`，禁止新增`物流公司`列；
- 真 CSV 输入应保留其编码、分隔符、引号和换行风格；当前 golden 必须保持 GBK/GB18030 兼容编码、逗号分隔和 LF 换行；
- 当前误命名 XLSX 样本若作为输入，只能提取字段后重新序列化为真 CSV，禁止原样返回。

## 11. ReviewCase 原因码

| reason_code | 触发条件 |
|---|---|
| `IMPORT_VALIDATION` | 必填字段、格式或时间非法 |
| `QUANTITY_SCALE` | 数量超过三位小数或 JD 数量不是正整数 |
| `CUSTOMER_MATCH` | 未命中客户档案 |
| `SKU_MATCH` | 未命中显式 SKU 映射 |
| `MAPPING_MULTIPLIER` | 乘数缺失、为0或非法 |
| `JD_CODE_CONFLICT` | 来源 JD 编码与维护映射冲突 |
| `CARRIER_MAPPING` | 快递公司缺少渠道映射 |
| `MULTI_SHIPMENT_SOURCE_FOLLOWUP` | 同一来源行出现多个 Shipment |
| `COD_AMOUNT_REQUIRED` | COD 没有可信金额 |
| `REVISION_AFTER_EXPORT` | 履约承诺后修改冻结字段 |

## 12. 状态推进

正常自动路径：

`NEED_REVIEW → READY_TO_EXPORT → WAITING_PROVIDER → TRACKING_RECEIVED → RETURN_FILE_READY → COMPLETED`

特殊路径：

- 缺货采购：`PROCUREMENT_IN_PROGRESS`；
- 业务失败：`EXCEPTION`；
- 多 Shipment：首批回填后回到 `NEED_REVIEW`，人工确认来源平台后续处理完成后进入 `COMPLETED`。

状态、业务事实、事件、版本和审计必须在同一事务提交。
