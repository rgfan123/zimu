# 来源订单附件 Agent 接入规格

## Problem Statement

运营收到来源订单 Excel/CSV 时，系统目前只有固定平台指纹解析器。文件表头未命中指纹会在原件留存前直接失败，现有履约单据 Agent 只会读取已经成功导入的批次，不能理解附件，也不能把未知模板提取为订单。运营因此必须等待开发补解析器，无法形成可审计、可复用的模板学习闭环。

同时，当前 Agent 工具循环把 8 轮写死为全局上限。这个保险丝既不能表达异步文件任务的真实预算，也不能保证大文件处理收敛。目标不是无限循环，而是以持久化任务、执行预算、重复调用检测和外部写对账形成可恢复的终止语义。

## Solution

增加“来源订单附件接入”能力。上传请求先把原件作为不可变证据保存并返回 `202 + job_id`；后台任务先尝试现有确定性解析器，模板未识别时将工作簿或 CSV 转成带单元格坐标的结构证据，由专用 Agent 只判断表头和字段语义，再由确定性映射器生成来源订单候选批次。

首个模板未识别批次必须由操作员整批确认。操作员可以同时勾选“信任此模板”，生成不可变、版本化的 TemplateProfile。后续来源渠道相同且模板结构指纹完全一致的文件，只有在全批通过确定性门禁时才自动放行。模板信任使用一个总开关，同时授权自动生成内部标准订单与自动提交京东发货；任一候选阻断都会让整批退回人工处理。

自动业务写通过系统 MCP 写工具进入既有应用用例，继续服从 Agent 白名单、`allow_write`、服务端身份、京东授权操作人、写门闩、幂等请求和 `RECONCILIATION_REQUIRED` 对账语义。模型只产生可验证的字段映射，不能直接决定来源渠道、SKU、客户身份、是否放行或是否重试外部写。

## User Stories

1. 作为运营人员，我想上传来源订单 `.xlsx`、`.xls` 或 `.csv`，立即拿到任务号，以便页面不会被大文件和模型调用长时间阻塞。
2. 作为运营人员，我想明确选择可信来源渠道，以便系统不根据文件内容猜测平台。
3. 作为运营人员，我想重复上传同一内容时获得同一个逻辑任务或既有结果，以便刷新和重试不会重复建单。
4. 作为运营人员，我想在任务页面看到接收、提取、待复核、导入、京东提交、完成、失败和待对账状态，以便知道当前责任方。
5. 作为运营人员，我想让已知指纹文件继续使用现有确定性解析器，以便成熟渠道不因 Agent 可用性退化。
6. 作为运营人员，我想让未命中固定指纹的文件自动进入通用证据提取，而不是直接 422，以便模板变化不再阻断业务。
7. 作为运营人员，我想查看 Agent 判断出的表头行、字段映射和每个订单字段的 Sheet/单元格证据，以便人工核对不是盲审模型 JSON。
8. 作为运营人员，我想在原始文件损坏、格式不支持或超过大小限制时看到稳定错误码，以便可以修复来源文件。
9. 作为运营人员，我想在模型未配置、超时或输出非法时保留原件和任务，以便证据不丢失并可转人工处理。
10. 作为运营人员，我想让同一来源订单的多商品行按稳定规则归组，以便不会拆错客户订单。
11. 作为运营人员，我想让缺字段、SKU 零/多匹配、地址不确定或疑似重复明确列为阻断项，以便模型置信度不能掩盖业务风险。
12. 作为运营人员，我想在任一候选有阻断时禁止整批自动建单和发货，同时保留正确候选，以便修复后继续而不是重新上传。
13. 作为授权操作员，我想整批确认首个模板未识别批次，以便候选转成内部标准订单并进入既有履约链路。
14. 作为授权操作员，我想在确认首批时额外勾选“信任此模板”，以便后续完全相同结构可以自动处理。
15. 作为授权操作员，我想看到模板结构指纹包含来源渠道、Sheet 结构、规范化表头和列顺序，以便知道信任的精确范围。
16. 作为授权操作员，我想让任何 Sheet、表头或列顺序变化自动生成新模板候选，以便旧信任不会漂移覆盖新结构。
17. 作为授权操作员，我想撤销某个模板版本的信任，以便后续文件立即恢复人工确认。
18. 作为运营人员，我想让受信模板在全批无阻断时自动创建 CanonicalOrder，以便减少重复审核。
19. 作为运营人员，我想让同一模板总开关同时控制自动成单与自动京东发货，以便授权状态没有两套漂移来源。
20. 作为仓储运营人员，我想让自动京东提交继续经过 Shipment 就绪、SKU/货号、结构化地址、版本和请求哈希门禁，以便模板信任不绕过仓储规则。
21. 作为仓储运营人员，我想让京东结果未知时任务进入 `RECONCILIATION_REQUIRED`，以便系统不会盲目再次建单。
22. 作为审计人员，我想追踪原件哈希、模板版本、Agent 运行、字段证据、人工信任、MCP 调用、订单和 Shipment，以便可以解释每次自动发货为何发生。
23. 作为平台管理员，我想让来源订单 Agent 的写工具必须显式白名单并启用 `allow_write`，以便其他业务 Agent 不会继承自动发货能力。
24. 作为平台管理员，我想用可配置执行预算替代固定 8 轮，以便交互 Agent 和异步文件 Agent 可以采用不同预算。
25. 作为平台管理员，我想在相同工具调用重复、无进展、总截止时间或预算耗尽时稳定终止，以便没有无限模型循环。
26. 作为开发人员，我想从公开提交、任务查询和 MCP 结果 seam 测试完整行为，以便内部 POI、模型或存储实现可以重构而不重写测试。
27. 作为开发人员，我想保留现有同步来源导入接口供既有连接器与兼容调用使用，以便新异步入口可以渐进上线。
28. 作为运营人员，我想在文件作业页面提交新任务、轮询状态、查看候选并确认/信任模板，以便不需要调用裸 API。

## Implementation Decisions

- 新增独立的来源订单附件接入模块，公开接口只负责提交任务、查询任务、确认候选和撤销模板信任；现有同步来源导入接口保留为兼容入口。
- 提交接口使用 multipart，要求可信 `source_channel`、导入模式和幂等键；校验扩展名、MIME、容器魔数和大小后，先以内容哈希保存原件，再创建持久化任务。
- 第一版接受 OOXML `.xlsx`、OLE2 `.xls` 和 CSV；图片、截图、PDF 与第三方履约自动提交不在范围内。
- 任务业务状态与通用异步队列状态分离。业务任务持久化当前阶段、稳定错误码、候选、模板、导入批次和外部写结果；通用队列继续提供租约、重试和重启恢复。
- 同一可信来源、文件内容哈希、导入模式和父修订批次组成内容幂等作用域。相同内容不得创建第二组订单或第二次外部写。
- 已知固定指纹优先走现有确定性解析器。只有明确的“零模板命中”进入 Agent fallback；多命中、损坏和安全校验失败不交给模型猜测。
- 工作簿证据提取模块隐藏 POI/CSV 细节，输出 Sheet 结构、表头候选、列顺序、单元格类型、脱敏样例与稳定坐标。原始 PII 不进入提示词；确定性映射器在本地原件上应用字段映射。
- 专用来源订单提取 Agent 使用结构化 JSON 输入和严格 JSON Schema 输出，只返回表头位置、字段到列的映射、订单归组键和无法解释项。
- 来源渠道由请求上下文提供；Agent 输出中不存在可覆盖来源渠道的字段。
- 来源订单候选批次在正式业务事实之前持久化，保留逐字段证据、原值、归一值、阻断项和提取版本。
- TemplateProfile 以来源渠道和模板结构指纹区分，版本不可变；结构指纹包含 Sheet 名称/顺序、表头位置、规范化表头和列顺序。
- 首批确认与模板信任是两个显式意图，可在同一命令提交。确认订单不自动信任模板；只有 `trust_template=true` 才建立 standing authorization。
- TemplateProfile 只有 `DRAFT/TRUSTED/REVOKED` 信任状态，不增加独立的自动成单和自动京东开关。`TRUSTED` 即同时授权两项自动业务写。
- 自动放行采用整批硬门禁。任一候选缺必填字段、数量非法、客户/订单归组不确定、SKU 不是唯一可用映射、地址不完整或疑似重复，整批保持 `NEEDS_REVIEW`，不创建任何 CanonicalOrder。
- 人工确认或自动放行均复用同一个 release 用例。该用例通过 MCP 写工具执行，先从候选生成来源导入批次和 CanonicalOrder，再确认批次并调用既有京东 Shipment 提交用例。
- MCP 输入只携带 `job_id`、期望版本、信任意图和幂等键；大体积候选从服务端持久化事实读取，不能由模型在工具参数中伪造。
- 京东提交继续要求服务端 Agent 身份、授权操作人、写模式、Shipment 计划、地址确认、SKU/货号、版本和请求哈希全部通过。
- 外部结果未知时任务与 Shipment 都进入可对账状态；同一外部写意图在完成对账前不可重试。
- Agent 运行时以执行预算替代固定 8 轮。预算至少包含总截止时间、模型调用数、工具调用数和重复工具调用阈值；异步任务在预算耗尽时保存检查点并以稳定状态收口。
- 文件作业页面改用异步入口，轮询任务并展示候选证据、阻断项、“确认本批次”和“信任此模板”动作。已知同步接口不从公开客户端删除。
- 所有用户可见枚举与错误码提供中文标签；未知值诚实回退技术原码。

## Testing Decisions

- 公开验收 seam 为：附件提交 HTTP 接口、任务查询/确认 HTTP 接口、MCP release 工具和既有京东外部写 Adapter；不直接测试私有 POI helper 或提示词拼装函数。
- 使用真实 PostgreSQL/Testcontainers 验证任务、候选、模板、幂等、租约、批次原子性和订单/Shipment 血缘。
- 使用最小真实 `.xlsx`、`.xls` 和 CSV fixture 验证容器识别、结构指纹、字段坐标及结构漂移；期望值来自固定人工样例，不从实现重新计算。
- Agent seam 使用可控 Runtime Adapter 返回固定列映射，覆盖成功、输出非法、超时、重复工具调用和预算耗尽；不 mock 自有领域模块。
- 京东只 mock 既有外部 SDK Adapter，验证写门闩、授权、幂等重放、请求漂移和结果未知；不降低现有 Shipment 门禁。
- API 测试覆盖：202 返回任务号、重复内容复用、未知模板转候选、首批确认、显式信任、结构漂移失效、整批阻断、受信模板自动放行和待对账收口。
- 前端单元测试覆盖：异步轮询终态、阻断项展示、信任勾选风险提示、整批不可放行和 `RECONCILIATION_REQUIRED` 展示。
- 最终运行后端针对性测试、完整 Maven 测试，以及前端 typecheck、unit tests 和 build；环境依赖失败与功能失败分别报告。

## Out of Scope

- 图片、截图、PDF、音频或视频订单识别。
- 根据文件内容猜测来源平台或自动新增 SourceChannel。
- 第三方履约方的自动文件发送或外部接口提交。
- 模型训练、在线微调或把人工确认数据发送给外部训练平台。
- 改变企微订单草稿逐单人工确认规则。
- 绕过京东地址确认、SKU 映射、写模式、授权操作人或对账门禁。
- 删除现有固定平台解析器或同步来源导入兼容接口。

## Further Notes

- 合并模板信任开关是用户明确选择，风险高于拆分授权：一次错误信任可能从内部订单传播到真实京东写入。ADR 0013 记录了该取舍与补偿门禁。
- “模板未识别”只描述结构未命中；“来源未归因”描述缺少可信 SourceChannel。两者不得混用。
- TemplateProfile 是可执行的业务映射契约，不是把整份原始文件或 PII 复制进提示词的缓存。
