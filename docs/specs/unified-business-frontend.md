# Spec：统一业务系统前端（履约 × 客户中心 × 原料库存）+ MCP 开放

状态：draft（待 seam 确认与切片评审）

关联 ADR：0002（单一应用外壳）、0011（antd 边界）、0012（知识归属深化）
关联规则：`docs/agents/navigation-admission.md`（菜单准入，硬上限 ≤6）

## Problem Statement

运营人员今天要在**三个互不相通的地方**才能看完一天的业务：

1. **履约中台**（子牧本体）——订单、履约、发货、回传，是唯一真正在用的系统；
2. **客户中心 kehuzx**——客户档案与客户跟进的权威来源。子牧侧的接入代码已经全部写完并进了生产镜像，但对端服务没部署、开关全关，所以「客户跟进」菜单点进去必然报 `KEHUZX_NOT_CONFIGURED`；
3. **原料库存 yuanliaokc**——记录公司首次数字化录入的原料与批次事实。它只有一个 stdio MCP 面，没有任何 HTTP 接口，也没有前端。今天只能通过 hermes 网关问答访问，业务人员在浏览器里根本看不到。

后果有三层：

- **看不全**：一个订单能不能发，取决于「客户是谁」（客户中心）和「原料够不够」（原料库存），但这两件事在履约界面里都看不到。
- **入口骗人**：「客户跟进」这个菜单是无条件显示的，不跟任何开关联动。用户点进去、录一单、点自动核对，拿到的一定是错误码——菜单在承诺一个系统给不出的能力。
- **MCP 权限是「不配置即全开」**：`MCP_MODULES` 留空时注册全部模块，而 `.env.example` 里根本没有这一行。生产之所以安全纯粹靠显式配置；任何照样例拉起的新环境会自动暴露全部工具，包括含客户姓名电话地址的 `followup` 模块。

## Solution

把三个系统收进**一个应用外壳**（ADR-0002 已定的那一个），让运营在同一套导航里完成一天的动线；同时把 MCP 的模块开放从「不配置即全开」改成「不配置即最小」，再按需显式开放。

统一**不是**把三个前端拼在一起，而是：

- **客户中心**：子牧原生页面 + 远端只读网关（`KehuzxReadGateway` 形态）。这条链路代码已存在，缺的是通电与两处契约补齐。
- **原料库存**：同一形态的第二条链路。前置是 yuanliaokc 侧先长出 HTTP MCP 面——它现在只有 stdio，而子牧 backend 在容器里，走 stdio 就得挂 docker socket，那是不可接受的安全降级。
- **外壳侧**：菜单准入按 `navigation-admission.md` 走，不突破 ≤6 硬上限；入口可见性与后端开关联动，不再出现「菜单承诺了系统给不出的能力」。
- **MCP**：`MCP_MODULES` 空值语义反转为 fail-safe，`.env.example` 补齐，再按业务需要显式开放模块。

## User Stories

1. 作为运营人员，我希望在同一套侧边栏里进入订单、发货、客户跟进和原料库存，这样我不用在多个系统之间切换和重新登录。
2. 作为运营人员，我希望「客户跟进」菜单只在客户中心真正接通时才出现，这样我不会点进一个必然报错的页面。
3. 作为运营人员，我希望在客户跟进页看到来自客户中心的客户档案事实，并且能看出哪些字段来自远端、取数时刻是什么，这样我知道自己看的是不是最新的。
4. 作为运营人员，我希望在客户跟进页把一个订单草稿关联到已有客户，这样我不用手工誊抄客户编码。
5. 作为运营人员，我希望在客户跟进页对未匹配的客户发起「创建新客户」，由系统生成客户编码，这样编码口径统一、不由人手工维护。
6. 作为运营人员，我希望客户中心的写操作必须经过人工确认，这样远端档案不会被自动流程悄悄改掉。
7. 作为运营主管，我希望每一次向客户中心的读取都留下存证（取数时刻与响应摘要），这样出现分歧时能复盘当时读到的是什么。
8. 作为运营主管，我希望客户中心读取失败时有独立的失败记录而不是静默降级，这样我能看出接口在什么时候不可用。
9. 作为运营人员，我希望在统一前端里看到原料库存的原料清单、批次与结存数量，这样我不用去问 Agent 或找人查。
10. 作为运营人员，我希望原料库存页面标明数据的最后更新时刻，这样我知道结存是什么时候的口径。
11. 作为运营人员，我希望原料库存页面在上游不可用时明确显示「取数失败」而不是显示 0 或空白，这样我不会把故障误读成没有库存。
12. 作为业务负责人，我希望原料库存作为**只读视图**先接进来，不承诺出入库写入，这样接入范围可控、不会把两个系统的库存事实写乱。
13. 作为运营人员，我希望原料库存入口出现在「商品与主数据」板块而不是每日动线板块，这样每日高频动线不被低频查询挤占。
14. 作为运营人员，我希望所有既有 URL 在改版后原样可达，这样我的书签和分享链接不失效。
15. 作为运营人员，我希望隐藏入口仍能直达并且侧边栏归属正确，这样我从别人发来的链接进入时不会迷失位置。
16. 作为系统管理员，我希望 `MCP_MODULES` 不配置时是最小开放而不是全部开放，这样新环境不会意外暴露含客户个人信息的工具。
17. 作为系统管理员，我希望 `.env.example` 里显式写出 `MCP_MODULES`，这样照样例拉起的环境有正确的默认。
18. 作为系统管理员，我希望配置了未知模块名时部署直接失败，这样拼错模块名不会被静默放行成全开。
19. 作为系统管理员，我希望在一处就能看出当前开放了哪些 MCP 模块与工具，这样我不用去容器里翻环境变量。
20. 作为外部 Agent 的接入方，我希望公网 MCP 端点只暴露被显式允许的模块，这样客户姓名电话地址不会从公网端点泄露。
21. 作为运营人员，我希望客户中心和原料库存的页面遵循与既有页面一致的密度与交互语言，这样我不需要重新学一套操作方式。
22. 作为开发者，我希望新增模块的接入形态和既有的远端只读网关一致，这样我不用为每个外部系统发明一套新做法。
23. 作为开发者，我希望外部系统的接入不绕过业务表边界（Connector 禁止直接写业务表），这样数据所有权保持清晰。
24. 作为开发者，我希望导航树的变更被自动门禁挡住，这样有人加菜单时必须同时更新准入清单与测试。
25. 作为业务负责人，我希望在「原料 ↔ SKU」映射尚未建立之前，系统不假装能回答「这单原料够不够」，这样我不会基于一个不存在的关联做决策。

## Implementation Decisions

### D1：统一 = 一个外壳，两类接入形态

沿用 ADR-0002：只有一个应用外壳，不新建第二个 SPA、不引入第二套导航。外部系统进入外壳有且只有两种形态：

- **形态 N（原生页）**：子牧前端页面 → 子牧后端 → **远端只读网关** → 外部系统。适用于需要与订单/履约事实并列展示、参与业务动线的数据。客户中心与原料库存都走这一形态。
- **形态 X（外部挂载）**：导航节点上的 `external` 字段，把外部系统自己的 UI 挂在同一外壳的一个路径下（既有先例：`管理驾驶舱 → /metabase`）。仅适用于**不参与业务动线的独立工具台**，不作为本 spec 的主路径。

选择形态 N 的理由：ADR-0002 明确否决过「让操作员在两套导航系统之间穿梭」；而客户档案与原料结存都要与订单事实并排看，属于动线内数据，不是独立工具台。

### D2：远端只读网关是唯一的跨系统读取形态

新增的原料库存接入**复用既有网关三件套的形状**（远端只读客户端 + 配置属性 + 读取网关），不复制客户中心那个大而全的工具类——后者的绝大部分体积来自「客户身份不能猜」带来的运行级作用域与个人信息白名单，原料库存没有这个约束。

网关必须保留的性质（这些是三件套里真正有价值的部分）：

- **SSRF 白名单**：端点的 host/port 显式钉死，不接受配置里的任意 URL；
- **契约漂移检测**：远端返回结构变化时给出稳定错误码而不是静默解析成空；
- **稳定错误码**：不可用、未配置、鉴权失败、契约漂移各有独立码，前端据此分别呈现；
- **读取存证**：每次远端读取落存证行（取数时刻 + 响应摘要），失败落独立失败行。

遵守既有边界：**外部系统一律通过接口接入，Connector 禁止直接写业务表。**

### D3：入口可见性与后端开关联动

导航树当前是纯静态常量，`hideInMenu` 是编译期字面量。为了让「客户跟进」「原料库存」在未接通时不出现，需要在外壳侧引入**运行期可见性**：外壳启动时读取一份后端下发的模块开放清单，据此过滤导航树。

这是本 spec 唯一的架构性新增。它替代的两个更差的选项：

- 构建期开关（`import.meta.env`）：一个镜像不能同时服务已接通和未接通的环境，与「同一镜像多环境」相冲突；
- 保持无条件显示：即当前状态，等于菜单在承诺系统给不出的能力。

导航树本身仍是单一事实源，运行期清单只做**过滤**，不新增节点、不改变路径，因此既有 URL 直达与侧边栏归属逻辑不受影响。

### D4：菜单准入

按 `docs/agents/navigation-admission.md` 的硬上限（每个一级板块可见子项 ≤6）：

- **客户跟进** 已在「我的工作台」，占位不变，仅改为受开关控制；
- **原料库存** 归入「商品与主数据」（当前 4 个可见叶子 → 5），不进「我的工作台」。判据：原料结存查询不是每日动线的必经环节，属主数据维护侧；且「我的工作台」已有 5 个可见叶子，逼近上限。

准入证据、计数更新与测试门禁按该文件第 1/3/5 节执行。

### D5：MCP 模块开放语义反转

`MCP_MODULES` 空值当前返回全部已知模块（向后兼容一期「注册即暴露」）。改为**空值 = 最小集**，并要求所有环境显式配置。

- 空值的最小集取值需要定案（见「Further Notes」的待定项 Q3）；
- 未知模块名继续 fail-fast（既有行为，保留）；
- `.env.example` 补齐 `MCP_MODULES` 行；
- 新增一个只读的「当前开放模块与工具」视图，供管理员核对，避免去容器翻环境变量。

已知模块清单（取证自各 provider 构造）：`default`、`masterdata`、`inventory`、`orders`、`orders-read`、`messages`、`followup`。生产当前显式配置为 `masterdata,inventory,orders-read`。

### D6：原料库存的接入范围限定为只读

本期只读：原料清单、批次、结存数量、最后更新时刻。**不做**出入库写入、不做订单原料占用、不做「这单原料够不够」。

理由是硬性的：子牧侧 `backend/src`、`frontend/src`、`docs/openapi.yaml` 中 `yuanliaokc` / `inventree` 命中数均为 0；`app.skus` 上没有任何 BOM 或原料字段；唯一的「原料」概念是商品档案上的自由文本 `商品原料 ProductIngredient`；唯一的 BOM 概念是**静态礼包 StaticBundle**，而它明确「礼包自身不创建 SKU、不单独计库存」。也就是说 **SKU ↔ 原料之间不存在任何连接键**。在这个映射建立之前，任何消耗/占用类功能都没有可计算的基础。

### D7：上游前置——yuanliaokc 需要 HTTP MCP 面

yuanliaokc 当前只有 stdio 传输（hermes 以 `docker exec -i` 接线）。子牧 backend 运行在容器内，若走 stdio 就必须挂载 docker socket，等于把宿主机 docker 控制权交给应用容器——不可接受。因此形态 N 的前置是 yuanliaokc 侧把传输改为 streamable-HTTP（或暴露其 REST 面），并在同一次变更中注入非默认密钥。

这是**另一个仓库的改动**，属跨仓协调，不在子牧侧可独立完成。

### D8：契约补齐

`task_type` 的取值集合在数据库 CHECK 与后端执行器上已支持两种，但契约与前端类型只声明了一种。补齐为联合类型，使三处一致。

## Testing Decisions

**什么是好测试**：只测外部可观察行为——导航树的可见叶子集合、页面在各错误码下的呈现、网关在远端异常时的错误码与存证落库结果。不测私有方法、不测组件内部状态、不对着实现细节写断言。

**seam 选择**（优先复用既有缝，尽量少）：

| Seam | 位置 | 已有 prior art |
|---|---|---|
| **S1 导航树** | 导航元数据单一事实源（不含 React） | `frontend/test/businessObjectNavigation.test.ts`——已对各分组子项做精确断言，加任何叶子都会红，是天然门禁 |
| **S2 页面组件** | vitest + jsdom 组件测试 | `frontend/test/*.test.tsx`（4 文件 / 17 用例，当前全绿） |
| **S3 远端只读网关** | 后端网关的对外行为（错误码 + 存证） | 客户中心侧既有网关契约测试 |
| **S4 MCP 注册表** | 模块过滤的对外行为（`tools/list` 与 `tools/call` 一致） | 既有注册表测试；注册期排除保证不存在「列表藏起来还能调用」的假隔离 |

四个 seam 中 S1/S2/S4 都是既有缝，S3 是既有形状的第二个实例。**没有新增 seam。**

**测试环境前置（硬性）**：项目 target 是 Java 21，本机 `mvn` 若落到 JDK 26 会产生与改动无关的假失败（`AGENTS.md` 已记载此陷阱）。本 spec 的所有后端验收必须在 JDK 21/24 下执行；当前本机 surefire 实际运行在 openjdk 26，需先纠正。

## Out of Scope

- **原料消耗与占用**：订单/礼包 → 原料的 BOM 展开、FEFO 预占与释放。前置是 SKU ↔ 原料映射，本期不建。
- **原料库存写入**：出入库、盘点、调拨。本期只读。
- **客户中心自身 UI 的挂载**（形态 X）：`/kehuzx` 路径挂载不在本期，本期只做原生页链路。
- **kehuzx 与 yuanliaokc 的部署本身**：属运维与跨仓协调，不是前端交付物；但它们是本 spec 多个切片的阻断前置，在票据里显式声明。
- **两个上游系统的既有安全问题修复**（上游默认密钥、未认证端点）：另行开票，不混入本 spec。
- **PII 掩码**：用户已决策全站不做（内部系统）。
- **访问埋点驱动的菜单降级**：`navigation-admission.md` 的前瞻条款，本期不启用。
